## [Unreleased]

### Added

- `delete()` on the query builder can send a lightweight `DELETE FROM` instead of `ALTER TABLE ... DELETE`: `MyTable::where('id', 1)->delete(true)`. ClickHouse hides the deleted rows before the call returns, so the next select no longer sees them. `ALTER TABLE ... DELETE` only queues a mutation that rewrites the data parts in the background. `delete(false)` sends `ALTER TABLE ... DELETE` as before. Lightweight deletes need a MergeTree-family table; ClickHouse rejects them on other engines, such as `Memory`, and on a table with projections unless the `lightweight_mutation_projection_mode` setting is `drop` (24.10 also accepts `rebuild`). Call `delete(false)` on such tables, or set it. On 24.8 it is a query setting: put it in the connection's `settings`, because `delete()` throws for a query with `settings()` (see Changed). From 24.9 it is a table setting, which you set with `ALTER TABLE my_table MODIFY SETTING lightweight_mutation_projection_mode = 'drop'`, and 24.10 ignores the query setting.
- The `use_lightweight_delete` connection option (`CLICKHOUSE_USE_LIGHTWEIGHT_DELETE` in `.env`) decides what `delete()` sends when you pass no argument. It defaults to `false`, so existing `delete()` calls keep sending `ALTER TABLE ... DELETE`. With `fix_default_query_builder` set to `false`, Laravel's own query builder follows it too.
- `delete()` and `update()` take a partition as their second argument and add `IN PARTITION` to the statement, so the mutation only touches that partition: `->delete(false, 202401)`, `->update(['v' => 'x'], '202401')`. An integer is sent as a number, a string as a quoted string, and an `Expression` such as `new RawColumn("ID '202401'")` as written. A lightweight delete in a partition (`DELETE FROM ... IN PARTITION`) needs ClickHouse 24.9 or later; older servers, 24.8 included, reject it with a syntax error.
- `truncate()` on the query builder sends `TRUNCATE TABLE <table>`, with `ON CLUSTER '<name>'` after `onCluster()` or with the `use_on_cluster` option (see below). It ignores where conditions. Like `delete()`, it quotes a table given to `table()` or `from()` part by part (see Changed): `DB::connection('clickhouse')->table('default.my_table')->truncate()` sends `` TRUNCATE TABLE `default`.`my_table` ``.
- `exists()` and `doesntExist()` on the query builder tell whether the query returns at least one row. They fetch at most one row of a constant (`SELECT 1 ... LIMIT 1`). A query whose columns cannot simply be replaced, because it uses aggregates, aliases, `withAlias()` names, `GROUP BY`, `HAVING`, `LIMIT BY`, a set operation or `orderByRaw()`, is wrapped in a subquery instead, so the answer matches what the query itself returns. The `ORDER BY rand()` of `inRandomOrder()` only sorts the rows, so the query is checked in place without it, as with an `orderBy()` column: `MyTable::where('field_two', 5)->inRandomOrder()->exists()` sends ``SELECT 1 FROM `my_table` WHERE `field_two` = 5 LIMIT 1``. The subquery of a set operation keeps its `ORDER BY`, which decides the rows a `LIMIT` keeps. When the query uses `INTERSECT` or `EXCEPT`, or reads rows from a query that does, in `from()`, a join, or a `withExpression()` or `withRecursiveExpression()` given a builder or a closure, at any depth, the query that `exists()` runs reads every column (`WHERE NOT ignore(*)`), because the analyzer of ClickHouse 24.8 otherwise compares only the columns that are read. Settings that act on the result, such as `offset` and `additional_result_filter`, are not supported: they act on the `SELECT 1` instead.
- `settings()` also takes a single setting: `->settings('max_threads', 4)`.
- Laravel's schema inspection methods work on ClickHouse connections. `Schema::getTables()`, `getTableListing()`, `getViews()`, `hasView()`, `getColumns()`, `getColumnListing()`, `getColumnType()`, `hasColumn()`, `hasColumns()`, `getIndexes()`, `getIndexListing()`, `hasIndex()`, `getForeignKeys()` and `hasForeignKey()` used to throw `This database driver does not support retrieving ...`. They read `system.tables`, `system.columns` and `system.data_skipping_indices` of the connection's database, or of the database you name.
  - `getTables()` leaves out views, materialized views with their inner tables, and dictionaries. `getViews()` lists views and materialized views. The `size` of a `Merge` table is `null`, because ClickHouse reports the bytes of its source tables for it.
  - Columns report the full ClickHouse type. A column is nullable when its type accepts `NULL`: `Nullable(...)`, `LowCardinality(Nullable(...))`, `Variant(...)`, `Dynamic`, or a `SimpleAggregateFunction` over one of them. `MATERIALIZED` columns are stored generated columns and `ALIAS` columns virtual ones.
  - Indexes are the primary key, named `primary`, and the data-skipping indices. Their columns are the elements of the key or index expression, such as `['id', 'intHash32(id)']`, without parentheses that enclose the whole expression: ClickHouse 26.8 prints the key of ``ORDER BY (`id`)`` as `(id)`, and its columns are `['id']` on every version. The `type` of the primary key is `null`, as on Laravel's SQLite driver, so `php artisan db:table` lists its attributes as `primary`, or `compound, primary` for a key of several columns. A data-skipping index has its type, such as `bloom_filter`.
  - `getForeignKeys()` returns an empty array, and `Schema::getCurrentSchemaName()` returns the connection's database instead of `null`.
- `php artisan db:show` and `php artisan db:table` work on ClickHouse connections. `db:show` failed with `Call to a member function getAttribute() on null`, because `Connection::getServerVersion()` read the version from PDO; it now runs `SELECT version()`. `Connection::getDriverTitle()` returns `ClickHouse`. `Connection::threadCount()`, which `db:show` prints as Open Connections, returns the number of client connections to the active node, the TCP, HTTP, MySQL and PostgreSQL connections that `system.metrics` counts, this one included; it returned `null`. `db:show --counts` counts the rows of every table and `--views` those of every view, so they fail on a table that ClickHouse cannot read, such as a `Kafka` or `Set` table, and on a parameterized view.
- Laravel's `DatabaseTruncation` testing trait works on ClickHouse connections. The trait wraps the truncation in `Schema::withoutForeignKeyConstraints()`, which threw a `BadMethodCallException`. ClickHouse has no foreign keys, so `disableForeignKeyConstraints()` and `enableForeignKeyConstraints()` now return `true` without sending a query. Every table that holds rows is truncated, except the migrations table.
  - Views, materialized views and dictionaries are left alone. A dictionary keeps the rows it has loaded until it is reloaded.
  - List three kinds of tables in `$exceptTables`. ClickHouse cannot read `Kafka`, `Set`, empty `File` and unreachable `URL` or `S3` tables, so they fail every test. It cannot truncate `Buffer`, `Merge`, `Null`, `URL`, `Kafka`, `GenerateRandom`, `MySQL` and `PostgreSQL` tables, or an `S3` table whose path has globs, so they fail as soon as they return a row. And `TRUNCATE` on an `S3` table deletes its object from the bucket.
  - On a connection with several nodes, only the active node is truncated, so a table that is not replicated keeps its rows on the other nodes, unless the connection sets the `use_on_cluster` option (see below), which truncates every node with `TRUNCATE TABLE ... ON CLUSTER`.
  - The README shows how to also empty the inner table of a materialized view, the rows waiting in a `Buffer` table and a table that is not replicated, and how to reload a dictionary.
- `whereNull()`, `orWhereNull()`, `whereNotNull()` and `orWhereNotNull()` on the query builder, and the same methods for `PREWHERE` (`preWhereNull()` …) and `HAVING` (`havingNull()` …), compile to `IS NULL` and `IS NOT NULL`. They take a column name, an `Expression` or an array of them. An array adds one condition per column, joined with the method's `AND` or `OR`.
- `whereEmpty()`, `orWhereEmpty()`, `whereNotEmpty()` and `orWhereNotEmpty()`, and the same methods for `PREWHERE` and `HAVING`, compile to ClickHouse's `empty()` and `notEmpty()`, which work on `String`, `Array` and `Map` columns. They take the same arguments as the NULL checks.
- `sample()` takes an optional offset: `sample(0.1, 0.5)` compiles to `SAMPLE 0.1 OFFSET 0.5`, and `getSampleOffset()` returns it. `sample(0.1)` still compiles to `SAMPLE 0.1`.
- `unionDistinct()`, `intersect()`, `intersectDistinct()`, `except()` and `exceptDistinct()` combine queries like `unionAll()`, from a builder or a closure. The queries added to one builder follow each other in call order without parentheses, so ClickHouse evaluates `INTERSECT` first, then `UNION` and `EXCEPT` from left to right. A builder or closure that has set operations of its own is one operand, in parentheses: `$a->except($b->unionAll($c))` compiles to `<a> EXCEPT (<b> UNION ALL <c>)`. The parentheses are left out where they cannot change the result: an operand of `unionAll()` whose own set operations are all `UNION ALL` is not put in parentheses, unless it has its own `WITH` clause or `INTERSECT` follows it. So nested `unionAll()` calls compile to the same SQL as in 3.0.0: `$a->unionAll($b->unionAll($c))` gives `<a> UNION ALL <b> UNION ALL <c>`. On ClickHouse 24.8, 26.3 and 26.8, a query that ends with an operand in parentheses fails with a syntax error when it has `settings()` and is used as a sub-query, in `from()`, `whereIn()`, `withExpression()` or another set operation; call `settings()` on the outer query instead. `getUnions()` still returns the queries, and `getUnionTypes()` returns their keywords. `exists()` and `count()` wrap such a query in a subquery, as they do with `unionAll()`. This builder has no `union()`, because ClickHouse rejects a bare `UNION` unless `union_default_mode` is set; Laravel's query builder sends `union distinct` for its `union()` (see Fixed).
- A `WITH` clause. `withExpression('name', $query)` adds a named sub-query, `` `name` AS (<query>) ``, from a builder, a closure, an `Expression` or a string of SQL. `withRecursiveExpression()` adds the same and makes the clause `WITH RECURSIVE`, which needs ClickHouse's analyzer (on by default from 24.8). `withAlias('alias', $value)` adds `` <value> AS `alias` ``: a builder or closure becomes a scalar sub-query, an array becomes an array literal, and other values are written like `where()` values. A name is quoted as one identifier, dots included, with its backticks and backslashes escaped: `withAlias('a.b', 1)` adds `` 1 AS `a.b` ``. The entries keep their call order in one clause before `SELECT`, and `getWiths()` returns them. A sub-query in `from()`, a join, `whereIn()` or a set operation compiles its own `WITH` clause.
- `SEMI`, `ANTI` and `ASOF` joins: `semiLeftJoin()`, `semiRightJoin()`, `antiLeftJoin()`, `antiRightJoin()`, `asofJoin()` and `asofLeftJoin()`, with the strictness constants `JoinStrict::SEMI`, `JoinStrict::ANTI` and `JoinStrict::ASOF`. `anyRightJoin()` and `allRightJoin()` are new as well, and so are `rightJoin()` and `fullJoin()`, which default to `ALL` like `leftJoin()`. `crossJoin()` adds a `CROSS JOIN` without join keys; a cross join with `USING` or `ON` keys, or with a strictness, throws a `GrammarException`. `JoinClause` gains `semi()`, `anti()`, `asof()`, `right()`, `full()` and `cross()`.
- `arrayJoin()` and `leftArrayJoin()` accept several arrays at once, with a string key as the alias: `arrayJoin(['tag' => 'tags', 'other'])` compiles to `` ARRAY JOIN `tags` AS `tag`, `other` ``. The aliases are not added to the select list. `ArrayJoinClause::getArrays()` returns the arrays and their aliases.
- `whereIn()`, `whereNotIn()`, `whereGlobalIn()`, `whereGlobalNotIn()`, `preWhereIn()`, `preWhereNotIn()`, `havingIn()`, `havingNotIn()` and their `or` variants accept a collection or any other `Arrayable`, and convert it with `toArray()`, as Laravel does: `whereIn('id', $users->pluck('id'))`. An empty collection works like an empty array (see Fixed). `where()`, `preWhere()` and `having()` convert a collection value, any `Illuminate\Support\Enumerable` such as a `Collection` or a `LazyCollection`, the same way, so `where('id', collect([1, 2]))` compiles to `` `id` IN (1, 2) ``. They do not convert another `Arrayable`, such as an Eloquent model, which throws an `InvalidArgumentException` there (see Changed). Before, a collection was left out and the query failed with a syntax error.
- `Schema::create()` on a ClickHouse connection creates the table that the blueprint declares: its columns with their modifiers, and the ClickHouse table clauses. In 3.0.0 it knew eight column types, threw a `BadMethodCallException` for the others, such as `uuid()`, `boolean()`, `decimal()` or `dateTime()`, and dropped every modifier (see Changed). The README section *Laravel's schema builder* lists the types and the rules.
  - The callback receives an `Oralunal\LaravelClickHouse\SchemaBlueprint`, which is Laravel's `Blueprint` with the table clauses `orderBy()`, `partitionBy()`, `sampleBy()`, `ttl()`, `settings()` and `ifNotExists()`, and the column types `array()`, `map()`, `ipv4()`, `ipv6()` and `date32()`. Laravel's `engine()`, `comment()` and `primary()` set the engine, the table comment and the sorting or primary key. A callback that type-hints Laravel's `Blueprint` keeps working. A blueprint resolver still decides the blueprint of the schema builder it is set on: after `$schema = Schema::connection('clickhouse')` and `$schema->blueprintResolver($resolver)`, `$schema->create()` passes the resolver's blueprint. The `Schema` facade gets a new schema builder for each call, so `Schema::blueprintResolver($resolver)` followed by `Schema::create()` still passes a `SchemaBlueprint`.
  - Column types: `char()`, `ulid()` and `foreignUlid()` give `FixedString(<length>)`, `float()` gives `Float64`, or `Float32` for a precision up to 24, `double()` `Float64`, `decimal()` `Decimal(<total>, <places>)`, `boolean()` `Bool`, `enum()` `Enum(...)`, `json()` and `jsonb()` `String`, and `date()` `Date`. `dateTime()` and `timestamp()` give `DateTime`, or `DateTime64(<precision>)` for a precision above 0, with the time zone of `->timezone()`. `year()` gives `UInt16`, `binary()` `String` or `FixedString(<length>)`, `uuid()` `UUID`, `ipAddress()` and `macAddress()` `String`, `geometry()` and `geography()` the geo type of their subtype, `vector()` `Array(Float32)`, and `rawColumn()` its type. `time()`, `timeTz()`, `set()` and `computed()` throw a `RuntimeException` (see Changed).
  - Column modifiers: `nullable()`, `default()`, `useCurrent()`, `storedAs()` (`MATERIALIZED`), `virtualAs()` (`ALIAS`) and `comment()`, and the ClickHouse modifiers `lowCardinality()`, `codec()`, `ttl()`, `ephemeral()` and `timezone()`, which `Oralunal\LaravelClickHouse\SchemaColumnDefinition` describes. A float default of a `Decimal` column is written as a string literal, `DEFAULT '19.99'`, because ClickHouse cuts `DEFAULT 19.99` off at the scale of the column and stores `19.98`.
  - An index with a ClickHouse index type, given as the third argument of `index()` or with `algorithm()`, goes into the column list with its `granularity()`: `index('url', null, 'bloom_filter(0.01)')->granularity(4)` adds ``INDEX `visits_url_index` `url` TYPE bloom_filter(0.01) GRANULARITY 4``. An index without a type sends nothing, unless the `default_index_type` option gives it one (see below).
  - Example: `Schema::create('events', fn (SchemaBlueprint $table) => [$table->id(), $table->string('name')->nullable()->default('x')->comment("it's"), $table->timestamps()])` sends ``CREATE TABLE `events` (`id` Int64, `name` Nullable(String) DEFAULT 'x' COMMENT 'it\'s', `created_at` Nullable(DateTime), `updated_at` Nullable(DateTime)) ENGINE = MergeTree() ORDER BY (`id`)``.
  - On a connection with a `cluster_name`, `Schema::create()` sends `CREATE TABLE ... ON CLUSTER` and, when the connection lists its nodes, makes a MergeTree engine replicated (see below and Changed). Without a `cluster_name`, it sends its statement to the active node only and keeps the engine as given, as in 3.0.0.
  - `temporary()` creates a temporary table inside `session()` and throws outside it (see below and Changed).
- The `engine` connection option (`CLICKHOUSE_ENGINE`) sets the engine of the tables that `Schema::create()` creates without `$table->engine()`. With `'engine' => 'ReplacingMergeTree'`, `Schema::create('events', fn ($table) => $table->id())` sends ``CREATE TABLE `events` (`id` Int64) ENGINE = ReplacingMergeTree ORDER BY (`id`)``. It defaults to `null`, which means `MergeTree()`, and a blank value counts as not set. Laravel's `migrations` table takes the option only when it is `MergeTree`, `ReplicatedMergeTree` or `SharedMergeTree` with its arguments alone, and `MergeTree()` otherwise, because another engine would merge or lose its rows (see Changed).
- The `exact_integer_types` connection option (`CLICKHOUSE_EXACT_INTEGER_TYPES`) gives each integer column of `Schema::create()` its own width, and `unsigned()` a `UInt` type: `tinyInteger()` is `Int8`, `unsignedTinyInteger()` `UInt8`, `smallInteger()` `Int16`, `unsignedSmallInteger()` `UInt16`, `integer()` `Int32`, `unsignedInteger()` and `increments()` `UInt32`, `bigInteger()` `Int64`, and `unsignedBigInteger()`, `id()` and `foreignId()` `UInt64`. It defaults to `false`, which keeps the types of 3.0.0: `tinyInteger()` is `Int16`, `unsigned()` is ignored and `id()` is `Int64`; only `unsignedSmallInteger()`, new in this release, gives `Int32`, so that its values fit. Turning the option on changes the tables that are created afterwards, and ClickHouse wraps a value that does not fit a narrower type without an error: `200` inserted into an `Int8` column reads back as `-56`. Laravel's `migrations` table keeps the columns of 3.0.0, `id Int32`, `migration String` and `batch Int32`, also with the option.
- `Schema::hasDictionary()` tells whether a dictionary exists, in the connection's database or in the database of a `<database>.<dictionary>` name. `hasTable()` is `false` for dictionaries now (see Changed).
- The `retry_on` connection option (`CLICKHOUSE_RETRY_ON`) decides which failed requests a connection with `retries` sends again. `any`, the default, sends every one again, as in 3.0.0. `unsent` sends a request again only when it never reached the server: the connection was refused, the host name was not found, or the connect timeout ran out. A request that timed out after it was sent, or that ClickHouse answered with an error, is not sent again. With `any`, a write that timed out on the client may still run on the server, and the retry runs it again: on ClickHouse 24.8, with `retries` set to `2`, an `INSERT` that timed out on the client stored its rows three times, and once with `unsent`. The option is read in any letter case, and `null` and `''` mean `any`. Any other value throws an `InvalidArgumentException` when the connection is created, also with `retries` set to `0`: `The [retry_on] option of the ClickHouse connection must be 'any' or 'unsent', [bogus] given.`
- `whereColumn()`, `orWhereColumn()`, `preWhereColumn()` and `orPreWhereColumn()` on the query builder compare two columns, as in Laravel: `whereColumn('updated_at', '>', 'created_at')` compiles to `` `updated_at` > `created_at` ``, and `whereColumn('a', 'b')` to `` `a` = `b` ``. A string is a column name, quoted part by part, and `raw()` is SQL. A list of `[first, second]` or `[first, operator, second]` arrays, or of `first => second` pairs, is one group in parentheses whose comparisons take the boolean of the call, as in Laravel 11 and later: `orWhereColumn([['a', 'b'], ['c', 'd']])` adds ``OR (`a` = `b` OR `c` = `d`)``. An entry may name its own boolean as a fourth value. A missing second column, an empty list or an entry of another kind throws an `InvalidArgumentException`.
- `whereExists()`, `orWhereExists()`, `whereNotExists()` and `orWhereNotExists()` on the query builder take a closure, which receives a new query, or a query builder of this package: `whereExists(fn ($query) => $query->from('users')->where('banned', 1))` compiles to ``EXISTS (SELECT * FROM `users` WHERE `banned` = 1)``. Any other argument throws an `InvalidArgumentException`. On ClickHouse 24.8, the analyzer compares only some of the columns of an `INTERSECT` or `EXCEPT` query inside `EXISTS`, so `EXISTS (<a> EXCEPT <b>)` was false although the `EXCEPT` returned a row; 25.8 and later compare them all. A sub-query that uses `INTERSECT` or `EXCEPT`, or reads rows from a query that does, through `from()`, a join, or a `withExpression()` of its own or of the outer query added before `whereExists()`, is therefore compiled to read every column: ``EXISTS (SELECT * FROM (<a> EXCEPT <b>) WHERE NOT ignore(*))``. ClickHouse 24.8 has no correlated sub-queries: a sub-query that reads a column of the outer query, such as `whereColumn('orders.user_id', 'users.id')`, fails with `UNSUPPORTED_METHOD` in a select. ClickHouse 24.8 would accept a mutation with it and then fail the mutation again and again, which holds back every later mutation of the table until `KILL MUTATION`, so `delete()` and `update()` refuse such a condition before the mutation is sent (see Changed). ClickHouse 26.3 and 26.8 run such a select, and refuse such a mutation themselves, at once.
- `whereAll()`, `whereAny()`, `whereNone()`, `orWhereAll()`, `orWhereAny()` and `orWhereNone()` on the query builder, and `preWhereAll()`, `preWhereAny()` and `preWhereNone()` with their `or` variants, compare several columns with the same operator and value, as `where()` compares one: `whereAll(['a', 'b'], '>', 1)` compiles to ``(`a` > 1 AND `b` > 1)``, `whereAny(['a', 'b'], 3)` to ``(`a` = 3 OR `b` = 3)``, and `whereNone(['a', 'b'], 1)` to ``NOT (`a` = 1 OR `b` = 1)``. Laravel adds no condition for an empty list of columns, but these methods throw an `InvalidArgumentException`, `whereAll(), whereAny() and whereNone() need at least one column.`, because the missing condition would make `delete()` or `update()` change more rows.
- `whereDate()`, `whereTime()`, `whereDay()`, `whereMonth()` and `whereYear()` on the query builder, with their `or`, `preWhere` and `orPreWhere` variants: `whereDate('created_at', '2024-01-05')` compiles to ``toDate32(`created_at`) = '2024-01-05'``, `whereTime('created_at', '>=', '9:05')` to ``formatDateTime(`created_at`, '%H:%i:%S') >= '09:05:00'``, `whereDay('created_at', '05')` to ``toDayOfMonth(`created_at`) = 5``, and `whereMonth()` and `whereYear()` to `toMonth()` and `toYear()`. `toDate32()` keeps the dates before 1970 and after 2149, where `toDate()` wraps around, and `formatDateTime()` gives the time of day in the column's time zone, where `toTime()` does not. A `DateTimeInterface` value is read in its own time zone. A day, a month or a year is written as an integer, because ClickHouse does not compare `toDayOfMonth()` with the text `'05'`, and a time is padded to `HH:MM:SS` without its fraction; its hour has one or two digits, and its minutes and seconds two, so `'7:8'` throws, where Laravel's query builder pads it to `'07:08:00'`. `null` compiles to `IS NULL` or `IS NOT NULL`, as in `where()`, and a list works with `IN`, `NOT IN`, `BETWEEN` and `NOT BETWEEN`. Any other value throws an `InvalidArgumentException`, such as `whereDay() takes an integer, a string of digits or a date, but 'fifth' was given.`
- `whereLike()`, `orWhereLike()`, `whereNotLike()` and `orWhereNotLike()` on the query builder ignore case, as in Laravel, with `ILIKE` and the new `Operator::NOT_ILIKE`, and compile to `LIKE` and `NOT LIKE` when their `caseSensitive` argument is `true`: `whereLike('field_one', 'error%')` compiles to `` `field_one` ILIKE 'error%' ``. ClickHouse uses the primary key for a `LIKE 'prefix%'` pattern, but not for `ILIKE`. `latest()` and `oldest()` order by `created_at`, or the column you pass, descending or ascending. `when()` and `unless()`, from Laravel's `Conditionable`, call a closure when a value is truthy or falsy. `inRandomOrder()` compiles to `ORDER BY rand()`; ClickHouse has no seeded random function, so `inRandomOrder(42)` throws an `InvalidArgumentException` that shows how to order by `cityHash64(42, id)` instead.
- `Connection::statementOnEveryNode()` sends a statement to every node of the connection, one after another, as `Migration::write()` does: `DB::connection('clickhouse')->statementOnEveryNode('SYSTEM RELOAD DICTIONARY my_dictionary')`. It logs the statement once, sends nothing while the connection pretends, returns `true`, and throws at the first node that fails, after the nodes before it have run the statement.
- `toArray()` on a model returns `attributesToArray()`: the attributes with the casts, accessors, `$appends`, `$hidden` and `$visible` applied. `BaseModel` still does not implement `Arrayable` or `JsonSerializable`, so `json_encode($model)` is unchanged; encode `$model->toArray()` instead.
- `first()`, `value()` and `getCollection()` on the query builder, where 3.0.0 failed with `Call to undefined method Oralunal\LaravelClickHouse\Builder::first()`. The rows are associative arrays, as `getRows()` returns them, not the `stdClass` objects of Laravel's query builder.
  - `first()` returns the first row, or `null`: `MyTable::query()->orderBy('created_at', 'desc')->first()` sends ``SELECT * FROM `my_table` ORDER BY `created_at` DESC LIMIT 1``. It reads within the query's own `LIMIT` and `OFFSET`, so `orderBy('id')->limit(10, 1)->first()` sends ``... ORDER BY `id` ASC LIMIT 1, 1``, and from the whole result of a set operation: ``SELECT * FROM (<a> UNION ALL <b>) LIMIT 1``. The columns given to it replace `*` on a query that selects every column, such as a model query or a query without a select list, and are ignored on a query with its own select list, as in Laravel.
  - `value('field_one')` returns one value of the first row. On a query that selects every column, it selects only that column, ``SELECT `field_one` FROM `my_table` WHERE `id` = 2 LIMIT 1``, and reads the value by its position, so an alias or an expression works: `value(raw('field_two + 1'))` sends `SELECT field_two + 1 FROM ...`. On a query with its own select list, it reads the column by the name that ClickHouse gives it, as `pluck()` does (see Changed), and throws an `InvalidArgumentException` for a column that the row does not have: `The query does not select the column [field_one] that value() reads.`
  - `getCollection()` returns the rows of `getRows()` in a Laravel `Collection`. `get()` still returns the smi2 `Statement`.
- `insertFiles()` on the query builder inserts the rows of files in an input format into the table of the query, one `INSERT` per file with the file as its body, through the smi2 client's `insertBatchFiles()`: ``DB::connection('clickhouse')->table('my_table')->insertFiles('/data/a.csv', 'csvwithnames', ['id', 'we`ird'])`` sends ```INSERT INTO `my_table` ( `id`,`we``ird` ) FORMAT CSVWithNames```. Each column name is quoted as one identifier, where `insertBatchFiles()` writes the names as given, so that a name taken from input could change the statement. The format is matched in any letter case against `TabSeparated`, `TabSeparatedWithNames`, `CSV`, `CSVWithNames`, `JSONEachRow`, `CSVWithNamesAndTypes` and `TSVWithNamesAndTypes`, and any other format throws an `InvalidArgumentException` before anything is sent. A path that is not a readable file throws an `Oralunal\LaravelClickHouse\Exceptions\QueryException`, `Cannot insert the file [/data/b.csv]: it is not a readable file. No file was sent.`, and so does a client that uses a ClickHouse session, inside `session()` or after the smi2 client's `useSession()`, both before any file is sent. The files are sent together, and the smi2 client throws for the first file that failed after every file was sent, so the other files may be inserted. Each file must be sent and inserted within the connection's `timeout_query`, and the connection's `retries` do not apply. `insertFiles()` returns the statement of each file, keyed by path, such as one whose `summary('written_rows')` is `'2'`, and logs each insert. While the connection pretends, it logs each insert and sends no file. On a query that a model starts, as in `MyTable::query()->insertFiles(...)`, it inserts into the model's `$tableSources`.

### Changed

- **Breaking:** **Security:** `min()`, `max()`, `sum()`, `avg()`, `average()` and `aggregate()` on the query builder quote a string column as a column name, part by part at its dots, with its backticks and backslashes escaped, as `select()` and Laravel's query builder do. 3.0.0 wrote it into the SQL as given, so a column taken from user input, as in `->max($request->metric)`, could add SQL to the query and read other tables: `max('(SELECT name FROM system.users LIMIT 1)')` returned a user name, and now fails with `UNKNOWN_IDENTIFIER`. `max('field_two')` sends ``SELECT max(`field_two`) AS `aggregate` FROM `my_table` ``, where 3.0.0 sent `SELECT max(field_two) AS aggregate FROM ...`, and `max('my_table.field_two')` gives ``max(`my_table`.`field_two`)``. Plain and dotted names return the same values as before, and a name with a space, such as `'my col'`, now works.
  - SQL in a string now fails with `UNKNOWN_IDENTIFIER`, because it is quoted as a name: `sum('a * id')`, `max('toDate(created_at)')`, `aggregate('count', ['DISTINCT grp'])` and the condition of `aggregate('sumIf', ['a', 'a > 1'])`. Pass SQL as `raw()`, a `RawColumn` or `DB::raw()`: `sum(raw('a * id'))` sends `SELECT sum(a * id) AS ...`, and `aggregate('count', [raw('DISTINCT grp')])` counts the distinct values. A name between backticks, such as ``max('`a`')``, is quoted with its backticks and fails; pass it without them. An integer column, as in `aggregate('sum', [1])`, is quoted as a name too; pass `raw('1')`. `'*'` is written as it is: `aggregate('count', ['*'])` gives `count(*)`.
  - `aggregate()` throws an `InvalidArgumentException` before anything is sent for a function name that is not a plain identifier, optionally followed by a list of numbers in parentheses: ``Invalid aggregate function name [max(1)) --]: a function name must match [A-Za-z_][A-Za-z0-9_]*, optionally followed by a list of numbers in parentheses, such as quantile(0.5).`` A parametric aggregate whose parameters are numbers works as before: `aggregate('quantile(0.5)', ['a'])` sends ``SELECT quantile(0.5)(`a`) AS `aggregate` FROM ...``, and so do `quantiles(0.5, 0.9)` and `topK(2)`. A parameter of another kind, such as the pattern of `sequenceMatch('(?1)(?2)')`, now throws; select such an aggregate with a `RawColumn` and read it with `value()`: `MyTable::select(new RawColumn("sequenceMatch('(?1)(?2)')(created_at, field_two > 0, field_two < 0)", 'matched'))->value('matched')`.
- **Behavior change:** A ClickHouse connection writes the bindings of `?` placeholders into the SQL itself, as ClickHouse literals, before it sends a query, where 3.0.0 handed them to the smi2 client as `:0`, `:1` and so on. This applies to `select()`, `statement()`, `insert()`, `update()`, `delete()`, `affectingStatement()` and `cursor()` on every ClickHouse connection, and to Laravel's query builder with `fix_default_query_builder` set to `false`, which binds every value with `?` now (see Fixed). `toSql()` of Laravel's query builder shows `?` where it showed `#@?`, as in `select * from "t" where "name" = ?`, and `QueryGrammar::parameter()` returns `?`. The query log, `DB::listen()` and the `QueryExecuted` event get the SQL with `?` and the bindings as given, where they got smi2's `:0`, as in `alter table "t" update "v" = ? where "id" = ?`. The connection no longer turns the `#@?` markers of 3.0.0 into `:0` (see below). A query whose number of `?` placeholders differs from its number of bindings throws an `InvalidArgumentException` before anything is sent: `The query has 1 "?" placeholder, but 2 bindings were given. Write a literal "?" as "??".` So does a query that mixes `?` with a `:0` or `{0}` of its list of bindings, or with a `{name:Type}` query parameter: `The query mixes "?" placeholders with smi2 placeholders (:0, {0}) or query parameters ({name:Type}). Use "?" for every binding.` A value that the package cannot write as a literal, such as a `stdClass` object, throws an `InvalidArgumentException`, where the smi2 client wrote its `value` property if it had one. **Breaking** for code that overrides `QueryGrammar::parameter()` or reads `#@?` or `:0` in the SQL that Laravel's query builder compiles or logs. **Breaking**, rarely, for raw SQL that has smi2's list placeholders and the `?` of the ternary operator, such as `DB::connection('clickhouse')->select('SELECT :0 > 1 ? 10 : 20 AS t', [5])`, which returned its row in 3.0.0 and now throws the mixing exception: write the ternary operator as `??`.
- **Breaking** for SQL that writes the `#@?` marker by hand: the connection no longer turns the `#@?` markers that Laravel's query builder wrote in 3.0.0 into `:0`, `:1` and so on in the SQL given to `select()`, `statement()` and `affectingStatement()`. A string literal keeps the marker: `select("SELECT '#@?' AS a")` returns `[['a' => '#@?']]`, where 3.0.0 returned `[['a' => ':0']]`. A `#@?` outside quotes is now `#@` followed by a `?` placeholder, so `select('SELECT #@? AS a', [5])` sends `SELECT #@5 AS a` and fails with `SYNTAX_ERROR`, where 3.0.0 returned `[['a' => 5]]`. Write `?`. `QueryGrammar::PARAMETER_SIGN` and `prepareParameters()` stay, deprecated and unused (see Deprecated).
- **Breaking** for code that extends `Builder`, and **Behavior change**: `Builder::insert()` is `insert(array $values, ?string $format = null): Statement`, and returns the statement of the insert, where 3.0.0's `insert(array $values)` returned nothing, so a subclass that overrides `insert(array $values)` fails to load. `$format` takes `'Values'` or `'JSONEachRow'` in any letter case, and `null` uses the connection's `insert_format` (see Added); any other format throws an `InvalidArgumentException` before anything is sent: `insert() takes the format 'Values' or 'JSONEachRow', [CSV] given.` The package now writes the `INSERT ... VALUES` itself, as the inserts of models do:
  - A float has every digit: `0.1 + 0.2` is written as `0.30000000000000004` and `1 / 3` as `0.3333333333333333`, where 3.0.0 wrote `0.3` and `0.33333333333333`, so `where('ratio', 1 / 3)` now finds the row. A computed float is cut off at the scale of a `Decimal` or integer column: `4.35 * 100` stores `434.99` in a `Decimal(10, 2)` column and `0.29 * 100` stores `28` in an `Int32` column, where 3.0.0 stored `435.00` and `29`. Round such a value first, as in `round(4.35 * 100, 2)`, or pass a numeric string or an int. `NAN`, `INF` and `-INF` are written as `nan`, `inf` and `-inf` (see Fixed), and dates follow `datetime_precision`.
  - `insert([])`, and a row without values, as in `insert([[]])` or `insert([['a' => 1], []])`, throw the smi2 client's `ClickHouseDB\Exception\QueryException`, `Inserting empty values array is not supported in ClickHouse`, before anything is sent, in both formats. 3.0.0 sent ``INSERT INTO `t`  VALUES  ()`` and got a `ClickHouseDB\Exception\DatabaseException` with `SYNTAX_ERROR`, so a `catch (DatabaseException $e)` no longer catches it.
  - PHP's `true` and `false` are still written as `'true'` and `'false'`, as the smi2 client wrote them, and a `Stringable` object with a public `value` property as its `value`.
- **Behavior change:** With `fix_default_query_builder` set to `false`, `Connection::query()`, `DB::table()` and the Eloquent models of the connection return `Oralunal\LaravelClickHouse\QueryBuilder`, a subclass of `Illuminate\Database\Query\Builder`, where 3.0.0 returned Laravel's class itself; **Breaking** only for code that compares the exact class. Its `count()` without a column, and the total of `paginate()`, count the rows that `get()` returns. A query with `groupBy()`, `distinct()`, `groupLimit()`, a select alias or expression, such as `selectRaw()` or `selectSub()`, or an order that defines an alias, calls `arrayJoin()`, adds rows with `WITH FILL`, or has `LIMIT`, `LIMIT ... BY`, `OFFSET`, `FETCH`, `UNION`, `INTERSECT` or `EXCEPT` in its raw SQL, is counted in a sub-query, without its `LIMIT` and `OFFSET`: `select('id as x')->where('x', 3)->count()` sends `select count(*) as "aggregate" from (select "id" as "x" from "my_table" where "x" = 3) as "aggregate_table"` and returns `1`, where 3.0.0 failed with `UNKNOWN_IDENTIFIER`. The count changes for these queries: `groupBy('user_id')->count()` returns the number of groups, with or without a select list, where 3.0.0 returned the number of rows of one group; `distinct()->select('user_id')->count()` returns the number of distinct rows, where 3.0.0 counted every row; and `selectRaw('count() as c')->count()` returns `1`, where 3.0.0 returned the number of rows of the table. A grouped query without a select list and with `having()` is counted the same way, where 3.0.0 failed with `NOT_AN_AGGREGATE`. `distinct('user_id')->count()`, which sends `count(distinct "user_id")`, `count($column)`, `sum()`, `avg()`, `min()`, `max()`, unions, other queries with `having()`, `limit()->count()` and plain queries are counted as Laravel counts them. A count in a sub-query evaluates the select list, so it can take longer than a count of the table.
- **Breaking** for code that compares the class of `app('migration.repository')` with `DatabaseMigrationRepository::class`: the package binds `Oralunal\LaravelClickHouse\ClickhouseMigrationRepository`, a subclass of Laravel's `DatabaseMigrationRepository`, in its place, so `instanceof DatabaseMigrationRepository` stays `true` (see Fixed). A repository of another class that the application or another package binds, a subclass of Laravel's included, is kept, and on other connections the repository works as Laravel's. **Behavior change** on a ClickHouse connection:
  - With `fix_default_query_builder` set to `false`, `getLast()`, `getMigrations()` and `getMigrationsByBatch()` return objects, as on Laravel's other connections, where 3.0.0 returned associative arrays. Laravel's migrator reads both, but code that calls the repository itself and reads `$row['migration']` breaks.
  - A migration is logged with `insert into "migrations" ("migration", "batch") settings insert_deduplication_token = ?, async_insert = 0 values (?, ?)` and three bindings, where 3.0.0 sent a plain insert of the two values, and the query log, `DB::listen()` and Telescope show it so. The row is the same. `async_insert = 0` writes the row before the insert returns (see Fixed). The token, the migration, the batch and 32 random hex digits, as in `2024_01_01_000000_create_events_table/1/<32 hex digits>`, keeps a row that is identical to an earlier one, such as the row of a migration that runs again after a rollback, in a `migrations` table that deduplicates inserts: a replicated table without `replicated_deduplication_window = 0`, as an `engine` option can make it, or a `MergeTree` table with a `non_replicated_deduplication_window`.
  - A rollback deletes the row with `alter table "migrations" delete where "migration" = ? settings mutations_sync = 1`, an `ALTER TABLE ... DELETE` whatever `use_lightweight_delete` and `use_on_cluster` say, where 3.0.0 sent it without `mutations_sync` (see Fixed). The log and the deletes go to the active node without `ON CLUSTER`, and a replicated `migrations` table passes them on to its other replicas. The delete usually takes less than 20 ms on ClickHouse 24.8 and 26.3. On 26.8, when the server has little RAM and its config does not set `background_pool_size`, ClickHouse lowers it from 16 to the RAM in GiB and the delete takes a few hundred milliseconds, and now and then more than 2 seconds, so `migrate:rollback`, `migrate:refresh` and `migrate:reset` can fail at the packaged `timeout_query` of 2 seconds with `Operation timed out after 2001 milliseconds with 0 bytes received`, after the migration's `down()` ran; the server still deletes the row.   - `deleteRepository()`, which `migrate` calls before it loads a schema dump, drops the table with ``DROP TABLE `migrations` SYNC``, or ``DROP TABLE `migrations` ON CLUSTER 'company_cluster' SYNC`` on a connection with a `cluster_name`, where Laravel's repository dropped it without `SYNC`.   - `migrate:install`, or the first `migrate`, creates the table with the columns of 3.0.0, also with the `exact_integer_types` and `engine` options: ``CREATE TABLE `migrations` (`id` Int32, `migration` String, `batch` Int32) ENGINE = MergeTree() ORDER BY (`id`)``. - **Behavior change:** `delete()`, `update()` and `insert()` on a query builder whose table comes from `table()` or `from()`, such as `DB::connection('clickhouse')->table('my-table')`, now quote the table name part by part, as a `SELECT` does: ``ALTER TABLE `my-table` DELETE ...``, ``INSERT INTO `default`.`my-table` ...``. - **Behavior change:** The query builder writes a float with every digit, where 3.0.0 wrote the 14 significant digits of PHP's string conversion. This applies to the values of `where()`, `preWhere()`, `having()` and their `or`, `In`, `NotIn`, `GlobalIn` and `Between` variants, `update()`, `withAlias()` and `Grammar::compileInsert()`, to the `?` bindings of raw SQL and of Laravel's query builder with `fix_default_query_builder` set to `false`, in its conditions, `update()` and `insert()` alike, and to `Connection::escape()`: `where('ratio', 1 / 3)` compiles to `` `ratio` = 0.3333333333333333 `` instead of `` `ratio` = 0.33333333333333 ``, `where('v', 0.1 + 0.2)` to `` `v` = 0.30000000000000004 `` instead of `` `v` = 0.3 ``, and `whereIn('w', [0.1, 2.0])` to `` `w` IN (0.1, 2.0) `` instead of `` `w` IN (0.1, 2) ``. A condition now finds a `Float64` value that was stored with every digit, such as `1/3`, which the 14 digits missed. A float computed in PHP is no longer rounded either, so it can miss a `Decimal` or integer value, and `update()` stores it cut off at the scale of the column, because ClickHouse reads the float as a `Float64` and cuts it off when it converts it: `4.35 * 100` is `434.99999999999994` in PHP, so `where('price', 4.35 * 100)` no longer matches a stored `435.00`, and `update(['price' => 4.35 * 100])` stores `434.99` in a `Decimal(10, 2)` column, where 3.0.0 stored `435.00`. `update(['cents' => 0.29 * 100])` stores `28` in an `Int32` column instead of `29`, and `where('d', 0.1 + 0.2)` no longer matches `0.30` in a `Decimal(10, 2)` column. In a condition, round such a value in PHP, as in `round(4.35 * 100, 2)`, which is written as `435.0`, or pass a numeric string, such as `'435.00'`. In `update()`, rounding does not help a value with a fraction: `update(['price' => round(19.99, 2)])` stores `19.98`, as `update(['price' => 19.99])` did in 3.0.0 and still does. Give `update()` a numeric string, such as `'19.99'`, or an int, as in `(int) round(0.29 * 100)`. The inserts store the float `19.99` as `19.99`, in 3.0.0 as now, because ClickHouse reads a number in the rows of an `INSERT ... VALUES` straight into the column's type. A computed float that an insert writes with every digit is cut off at the scale of the column: with `fix_default_query_builder` set to `false`, `DB::table('t')->insert(['price' => 4.35 * 100, 'cents' => 0.29 * 100])` stores `434.99` in a `Decimal(10, 2)` column and `28` in an `Int32` column, where 3.0.0 stored `435.00` and `29`, and so do an `INSERT` with `?` bindings, the inserts of models and the `insert()` of the package's query builder, which write every digit too (see the next entries). Round such a value in PHP first, as in `round(4.35 * 100, 2)`, which stores `435.00`, or pass a numeric string or an int. The named bindings of raw SQL, such as `:ratio`, which the smi2 client writes, still send 14 significant digits, as 3.0.0 did. So a float that they stored, or that 3.0.0 stored, no longer equals the same PHP float in a condition of either query builder: after `DB::connection('clickhouse')->table('t')->insert([['ratio' => 1 / 3]])` in 3.0.0, which stored `0.33333333333333`, as every insert of 3.0.0 did, `where('ratio', 1 / 3)` finds no row, where 3.0.0 found it. Round such a float in PHP before you insert and compare it, as in `round($ratio, 6)`, or compare with a range, as in `whereBetween('ratio', [$ratio - 1e-9, $ratio + 1e-9])`.
- **Behavior change:** `InsertArray::TYPE_DECIMAL` writes each item with every digit, as the query builder writes a float, where 3.0.0 wrote the 14 significant digits of PHP's string conversion: `new InsertArray([1 / 3, 0.1 + 0.2], InsertArray::TYPE_DECIMAL)` writes `[0.3333333333333333,0.30000000000000004]` instead of `[0.33333333333333,0.3]`, and a whole number gets a fraction, so `['1.5', '2', 3]` gives `[1.5,2.0,3.0]` instead of `[1.5,2,3]`. `INF` and `-INF` are written as `inf` and `-inf` instead of `INF` and `-INF`, which ClickHouse stores the same, and `NAN` as `nan` (see Fixed). The inserts send this text in the `Values` format: `insertAssoc()`, `insertBulk()`, `create()`, `save()`, `insert()` and the buffers; the `JSONEachRow` format sends the items (see Added). An `Array(Float64)` column now stores every digit. An `Array(Decimal(10, 2))` or `Array(Int32)` column cuts a computed float off: `4.35 * 100` stores `434.99` or `434`, where 3.0.0 stored `435`. - **Behavior change:** The inserts of models write a float with every digit, where 3.0.0 wrote the 14 significant digits of PHP's string conversion: `insertAssoc()`, `insertBulk()`, `prepareAndInsert()`, `prepareAndInsertAssoc()`, `prepareAndInsertBulk()`, `create()`, `save()` and `flushBuffer()`, also for the floats in an array. `insertAssoc([['ratio' => 1 / 3, 'arr' => [0.1 + 0.2]]])` stores `0.3333333333333333` and `[0.30000000000000004]`, where 3.0.0 stored `0.33333333333333` and `[0.3]`, so `where('ratio', 1 / 3)` now finds the row. A computed float is cut off at the scale of a `Decimal` or integer column: `4.35 * 100` stores `434.99` in a `Decimal(10, 2)` column and `0.29 * 100` stores `28` in an `Int32` column, where 3.0.0 stored `435.00` and `29`. Round such a value in PHP first, as in `round(4.35 * 100, 2)`, or pass a numeric string or an int. A whole float is written without a fraction, as before, and `NAN`, `INF` and `-INF` as `nan`, `inf` and `-inf` (see Fixed). While the rows are written, PHP's `precision` setting is `-1`, so a `Stringable` value whose `__toString()` casts a float to a string gets every digit too. The package now writes the `INSERT` itself, as the smi2 client's `Client::insert()` wrote it, and sends it with `Client::write()`, in the same HTTP request, so only code that replaces or mocks `Client::insert()` on the connection's client sees a difference. - **Behavior change:** `select()`, `scalar()`, `selectOne()`, Laravel's query builder with `fix_default_query_builder` set to `false`, `selectParallelly()` and the SQL and Laravel entries of `Parallel` throw an `Oralunal\LaravelClickHouse\Exceptions\QueryException`, which is a `ClickHouseDB\Exception\QueryException`, before anything is sent or logged, when the `FORMAT` clause of the query names a format other than `JSON`, `JSONStrings`, `JSONCompact` and `JSONCompactStrings`, which they still read rows from, in any letter case: `Cannot read rows from a query whose FORMAT clause names XML: select() and parallel queries read the rows of a JSON result (JSON, JSONStrings, JSONCompact, JSONCompactStrings). In 3.0.0, these queries were sent: `XML`, `Pretty`, `Values` and `Null` failed with `SYNTAX_ERROR` (`... FORMAT XML FORMAT JSON`), `CSV`, `TSV` and `JSONEachRow` failed with ``Can`t find meta`` after the query ran, or returned no rows for an empty result, and `JSONCompactEachRow` returned no rows although rows matched. The `FORMAT` clause is the word `FORMAT` and a name at the end of the query, before `SETTINGS` and `;` only, outside string literals, quoted names, comments, heredocs and parentheses. A column, an alias or a table named `format`, as in `ORDER BY format DESC`, `WHERE format IN ('csv')` or `SELECT * FROM format(CSV, '1')`, is no `FORMAT` clause, and such a query runs as in 3.0.0. `cursor()`, which asks for `JSONEachRow` itself, refuses every `FORMAT` clause, `JSON` included (see Fixed).
- **Behavior change:** On a client that uses a ClickHouse session, as after the smi2 client's `useSession()`, a lightweight delete, a `delete()`, `update()`, `truncate()` or `MyTable::optimize()` with `ON CLUSTER`, and, on a connection with a `cluster_name`, a schema statement with `ON CLUSTER`, of a table name that a temporary table of the session has, throw `QueryException::cannotReachTemporaryTable()` before anything is sent (see Added). In 3.0.0, such a statement changed the table of the database, on every node with `ON CLUSTER`, or failed with `UNKNOWN_TABLE`. Each such statement sends one `EXISTS TEMPORARY TABLE` first, and `delete()` and `update()` send the check of a condition with a sub-query outside the session.
- **Behavior change:** **Data safety:** `insertAssoc()` and `prepareAndInsertAssoc()` filled a key that a later row lacked with the position of the key in the first row: `insertAssoc([['id' => 5, 's' => 'x'], ['id' => 6]])` stored `s = '1'` for the row 6, and a missing `boolean` cast column became `0` after the casts. Such a batch now throws the smi2 client's `ClickHouseDB\Exception\QueryException`, `Fields not match: id and id,s on element 1`, and nothing is inserted: give every row every key, or insert such rows in separate calls. Rows with the same keys in another order are inserted as before, and an extra key in a later row, or a key missing from the first row, threw `Fields not match` in 3.0.0 too. `BaseModel::normalizeAssocRowKeyOrder()`, which filled the keys, is no longer called (see Deprecated).
- **Behavior change:** `flushAllBuffers()`, called on a model that uses the `HasBufferedInserts` trait again, flushes every model that has buffered rows, as its documentation says, not only that model and its children (see Fixed). A model whose flush fails keeps its rows: with `silent: true`, the failure is reported and the other models are flushed; without it, the first failure is thrown.
- The package is tested on ClickHouse 24.8, 26.3 and 26.8. The README section *Newer ClickHouse versions* lists what 26.3 and 26.8 do otherwise than 24.8 with their default settings, such as 64-bit integers returned as JSON numbers from 25.8, asynchronous inserts, the parsing of dates with a sub-second part and the slower mutations of 26.8 on a server with little RAM, and the settings that bring back the behavior of 24.8.

### Deprecated

- `asyncWithQuery()`, `getAsyncQueries()`, `toAsyncSqls()` and `toAsyncQueries()` of the query builder. `get()` never ran the queries that `asyncWithQuery()` adds, only the query it is called on, and `toAsyncQueries()` has failed since 2.0.0 (see Fixed). To run several queries at the same time, use `Parallel::get([$query, $otherQuery])`, or `Parallel::getRows([$query, $otherQuery])` for their rows, and `Parallel::getRows($query->getAsyncQueries())` for the queries that `asyncWithQuery()` added (see Added). The smi2 client's own `selectAsync()` with `executeAsync()` sends each request once, whatever `retries` says, and throws `QueryException::cannotRunAsynchronouslyInSession()` inside `session()`.
- `QueryGrammar::PARAMETER_SIGN` and `QueryGrammar::prepareParameters()`. Laravel's query builder no longer writes `#@?`, and `prepareParameters()` returns SQL without it as it is. They will be removed in 4.0.
- `BaseModel::normalizeAssocRowKeyOrder()`. `insertAssoc()`, `prepareAndInsertAssoc()` and `buffer()` no longer call it, because it filled a key that a row lacked with a made-up value (see Changed); they reorder the keys of each row without filling any. A model that overrides it to fill missing keys no longer changes the rows, and such a batch throws `Fields not match`. The method keeps its signature and behavior for subclasses that call it, and raises no deprecation notice.

### Removed

- **Breaking:** `BaseModel::usesTimestamps()`, `getRelationValue()`, `relationResolver()` and `relationLoaded()`. They existed only for Eloquent's `HasAttributes` trait and always returned `false` or `null`. Eloquent's `isRelation()` and `relationsToArray()`, which came with that trait, are gone as well; `relationsToArray()` threw a `TypeError`. A call to one of them now fails with `Call to undefined method`. `getCasts()` and `preventsAccessingMissingAttributes()` stay, with the same signatures; they now come from `Oralunal\LaravelClickHouse\Concerns\HasAttributes`.
  - A model that declares one of these methods still loads, but the package no longer calls it. `getDates()` returns `[]` without asking `usesTimestamps()`: when a model's `usesTimestamps()` returned `true`, the columns that its `getCreatedAtColumn()` and `getUpdatedAtColumn()` name were date columns, which stored a `Carbon` value as a string in `$dateFormat` and read back as `Carbon`. Cast them in `$casts` instead, for example `'created_at' => 'datetime'`. Reading a key that has no value no longer calls `getRelationValue()`, which it did when the model had a method of that name or when its `relationLoaded()` or `relationResolver()` accepted the key; the key reads as `null`. Use an accessor instead.
  - The protected methods of Eloquent's trait that `BaseModel` never called, or that only relationships, timestamps and Eloquent's own inserts and updates used, are gone too, such as `initializeHasAttributes()`, `casts()`, `getRelationshipFromMethod()`, `getAttributesForInsert()` and `getDirtyForUpdate()`. `class_uses(BaseModel::class)` lists `Oralunal\LaravelClickHouse\Concerns\HasAttributes` instead of Eloquent's trait.

### Fixed

- `delete()` and `update()` ignored `onCluster()`. On a table that is not replicated, the mutation therefore only reached the node the connection talks to. They now send `ON CLUSTER '<name>'` after the table name.
- `delete()` and `update()` ignored `preWhere()` conditions, so they deleted or updated more rows than the query selects: `MyTable::where('field_two', '<', 0)->preWhere('created_at', '<', '2024-01-01 00:00:00')->delete()` deleted every row with a negative `field_two`, whatever its date. A mutation has no `PREWHERE`, so the prewhere conditions now join the where conditions: ``ALTER TABLE my_table DELETE WHERE (`created_at` < '2024-01-01 00:00:00') AND (`field_two` < 0)``. A query with only `preWhere()` conditions used to fail with a syntax error and now changes the rows they select. Queries without `preWhere()` send the same SQL as before.
- **Data safety:** `delete()` and `update()` used only the where conditions of the query and ignored the clauses that decide which rows it selects, so they changed rows that the query does not select. In 3.0.0, `MyTable::where('field_two', '<', 0)->orderBy('created_at')->limit(2)->delete()` sent ``ALTER TABLE my_table DELETE WHERE `field_two` < 0`` and deleted every row with a negative `field_two`, and a join, `sample()`, `arrayJoin()`, `groupBy()`, `having()`, `limitBy()` or `unionAll()` was ignored the same way. So were `final()`, settings that limit the rows, such as `settings(['limit' => 1])`, a `from()` sub-query from a builder or a closure in a query that `MyTable::where()` starts, an `orderByRaw()` that calls `arrayJoin()`, which drops the rows whose array is empty, and a select alias: a condition on the alias read the table's column of that name. The same held for an `ORDER BY` entry that defines an alias, which ClickHouse also lets the where and prewhere conditions read: on a table `oa` with the columns `a` and `b` and the rows `(1, 10)`, `(2, 20)`, `(3, 30)` and `(10, 1)`, the query `select('a')->where('b', '<', 5)->orderBy('a as b')` selects the rows where `a` is 1, 2 and 3, but its `delete()` sent ``ALTER TABLE oa DELETE WHERE `b` < 5`` and removed `(10, 1)`, the only row that the query does not select. `orderByRaw('a AS b')`, a `Column` with `as()` and a `RawColumn` with an alias were ignored the same way. With `fix_default_query_builder` set to `false`, Laravel's `delete()` ignored `limit()`, `groupLimit()`, `offset()`, `groupBy()`, `having()`, such an `orderByRaw()`, an order that defines an alias, such as `orderBy('a as b')` or `orderByRaw('a AS b')`, unions and select aliases too, and so did `delete()` and `update()` for an `orderByRaw()` with `LIMIT`, `LIMIT ... BY`, `OFFSET` or `FETCH` in it, which ClickHouse reads as clauses of the select: `where('id', '>', 0)->orderByRaw('ts desc limit 1 by user')->delete()` sent ``alter table "t" delete where "id" > 0`` and deleted the rows of every user, though the query selects one row of each. These queries now throw a `QueryException` (see Changed). To change the rows that such a query selects, select their keys first: `MyTable::where('id', $query->pluck('id'))->delete()`. The README explains when the query as a sub-query is not the same.
- `prepareAndInsert()` and `prepareAndInsertBulk()` threw a `TypeError`, such as `Oralunal\LaravelClickHouse\BaseModel::prepareFromRequest(): Argument #2 ($columns) must be of type array, string given`, after the PHP deprecation `Use of "static" in callables is deprecated`: they passed the column list to `array_map()` as a second array. They now call `prepareFromRequest()` with each row and the column list, and insert the rows. `prepareAndInsertAssoc()` no longer raises that deprecation.
- `new InsertArray([])`, and an empty `InsertArray::TYPE_STRING_ESCAPE`, inserted an array that holds one empty string, `['']`. They now insert an empty array, as `TYPE_INT` and `TYPE_DECIMAL` did.
- The query builder doubled the backticks in the names it quotes, but not the backslashes, which ClickHouse reads as escape characters inside backticks. A column named `a\b` was written as `` `a\b` ``, which ClickHouse reads as another name, and a name that ends with a backslash, such as `ends\`, failed with a syntax error. Backslashes are now doubled as well, in column, alias, table and database names and in `Grammar::compileInsert()`: `` `a\\b` ``. Names without a backslash are written as before.
- `final(false)`, and `false` as the `$isFinal` argument of `from()` or `table()`, wrote `FINAL` as well, because the query builder wrote it whenever the option was set: `MyTable::select()->final(false)` compiled to ``SELECT * FROM `my_table` FINAL``. On a plain `MergeTree` table such a query failed with `ILLEGAL_FINAL`, and on a `ReplacingMergeTree` table it merged the rows as `final()` does. Now `false` leaves `FINAL` out, as when the option is not set; `true`, and `final()` without an argument, still write it.
- On the query builder, `where('col', $value, null)` with a value that is not an operator compiled to a bare `` WHERE `col` ``. A Laravel-style helper such as `fn ($column, $operator = null, $value = null) => $query->where($column, $operator, $value)` sends exactly that, and on a `UInt8` or `Bool` column `where('processed', 0, null)` then selected, deleted or updated the rows where `processed` is `1`. With a `null` third argument, a second argument that is not an operator is now the value, as in Laravel: `` `processed` = 0 ``, or `IN (...)` for an array. `orWhere()`, `preWhere()`, `having()` and their `or` variants behave the same way, and so does `MyTable::where()`.
- `delete()` and `update()` without a where or prewhere condition sent a statement ending in `WHERE `, which ClickHouse rejects with a syntax error. They now throw `Oralunal\LaravelClickHouse\Exceptions\QueryException` without sending anything. To remove every row, call `truncate()`; to update every row, add `whereRaw('1')`. Any condition counts, including the `1 = 1` of an empty `whereNotIn()` list (see Changed). With `fix_default_query_builder` set to `false`, Laravel's `delete()` and `update()` without a where condition throw the same exception; `delete()` used to send an `alter table ... delete` statement without a condition.
- `settings(['optimize_move_to_prewhere' => false])` sent `optimize_move_to_prewhere=''`, which ClickHouse rejects. It now sends `0`. A single quote in a string value broke the query, and a backslash was read as the start of an escape sequence; both are now escaped.
- `MyTable::where('col', '=', null)` compiled to ``WHERE `col` = '='``: the model passed only the column and the operator to the builder, which took the operator for the value. `MyTable::where(fn ($query) => ...)` compiled to an incomplete `WHERE (...) =`. The model now passes its arguments to the builder as given, so `MyTable::where(...)` builds the same condition as `MyTable::select()->where(...)`.
- With `fix_default_query_builder` set to `false`, `DB::connection('clickhouse')->table(...)->update([...])` sent Laravel's `update ... set ...`, which ClickHouse 24.8 rejects with a syntax error. It now sends `alter table ... update ...`, with an array or a collection value written as an array literal: `where('id', 1)->update(['tags' => ['a', 'b']])` sends `alter table "t" update "tags" = ['a', 'b'] where "id" = 1`. An associative array loses its keys, so write a `Map` with `DB::raw("map('k', 1)")`.
- `Schema::hasTable()` put the database and table names into the query without escaping them, so a name containing `'` or `\` caused a syntax error. They are now escaped.
- `Schema::hasTable('analytics.events')` looked for a table named `analytics.events` in the connection's database and returned `false`. It now looks for `events` in the `analytics` database, as Laravel's other drivers and the schema inspection methods above do. A name with a dot is read as `<database>.<table>`.
- Conditions with a date, a boolean, an enum, a `Stringable` value or a value object of the smi2 client sent incomplete SQL to ClickHouse: `where('created_at', '>', now())` became ``WHERE `created_at` >`` and `where('active', true)` became ``WHERE `active` =``. These values are now written as literals in `where()`, `preWhere()`, `having()`, their `or`, `In`, `NotIn`, `GlobalIn` and `Between` variants, `update()` and `Grammar::compileInsert()`. A `DateTimeInterface` (Carbon included) becomes `'Y-m-d H:i:s'` in its own time zone, `true` and `false` become `1` and `0`, a backed enum becomes its value, a pure enum its quoted name, a value object of the smi2 client a literal of its type, such as `18446744073709551615` for `UInt64::fromString('18446744073709551615')` and `map('k', 1)` for `MapType::fromArray(['k' => 1])`, an expression of the smi2 client its SQL, such as `now()` for `new Raw('now()')`, and any other `Stringable` a quoted string. A collection is `Stringable` too, but is never written as a string: it is a list of values or throws (see Added and Changed). Dates keep second precision, the format inserts and bindings use by default, so the sub-second part is dropped, unless the connection's `datetime_precision` is `microsecond` (see Added). ClickHouse does not compare a `Date` or `Date32` column with such a literal, so pass `$date->format('Y-m-d')` for those columns.
- `where('col', null)` and `where('col', '=', null)` sent ``WHERE `col` =``. They now compile to `` `col` IS NULL ``, and so does `where('col', null, null)`, which compiled to a bare `` WHERE `col` ``. `!=` or `<>` with `null` compiles to `` `col` IS NOT NULL ``. `orWhere()`, `preWhere()`, `having()` and their `or` variants behave the same way, and so does `MyTable::where('col', null)`. This only applies when `null` is passed as the value and the column is a name or an `Expression`; `where('col')` is unchanged.
- `where('col', '<>', 1)`, and `<>` in `orWhere()`, `preWhere()`, `having()` and their `or` variants, threw an `UnexpectedValueException` (`Value '<>' is not part of the enum`). `<>` now compiles to `!=`.
- A `CROSS JOIN` could not be built: `join($table, null, JoinType::CROSS)` threw a `GrammarException` asking for a strictness and join keys, and with join keys it built SQL that ClickHouse rejects. It now compiles to `CROSS JOIN <table>`.
- `Grammar::compileInsert()` wrote a PHP array value as `Array`, with a PHP warning, and a query without a table as `INSERT INTO null`. It now writes an array literal such as `['a', 'b']` and throws a `GrammarException` when the table is missing. `insert()`, `insertAssoc()` and `insertBulk()` do not use it.
- `update()` wrote an array value as `Array`, with an `Array to string conversion` warning, so the mutation failed. It now writes an array literal: `update(['tags' => ['a', 'b']])` sets `` `tags` = ['a', 'b'] ``.
- A nested array in an `IN` list, as in `whereIn(raw('(id, name)'), [[1, 'a'], [2, 'b']])`, was written as `Array`, with an `Array to string conversion` warning. It now compiles to a tuple: `(id, name) IN ((1, 'a'), (2, 'b'))`.
- An empty list in an `In` method lost the `OR` of the call or failed. `where('b', 1)->orWhereIn('a', [])` compiled to ``WHERE `b` = 1 AND 0 = 1`` and returned no row. `whereNotIn()` and `orWhereNotIn()` added no condition, so in an `OR` they matched too few rows: `whereNotIn('a', [])->orWhere('b', 1)` compiled to ``WHERE `b` = 1``. `preWhereIn()`, `havingIn()`, `whereGlobalIn()`, their `NotIn` and `or` variants, and `where('a', [])` compiled to an empty list, such as `` `a` IN () ``, which ClickHouse rejects. Every `In` method, and an empty array or collection in `where()`, `preWhere()` and `having()`, now compiles an empty list to `0 = 1` for `IN` and `GLOBAL IN` and to `1 = 1` for `NOT IN` and `GLOBAL NOT IN`, with the `AND` or `OR` of the call: ``WHERE `b` = 1 OR 0 = 1``.
- `where()`, `preWhere()` and `having()` threw a PHP error, such as `Call to a member function getFirstElement() on int`, for an array with `GLOBAL IN` or `GLOBAL NOT IN`, with `BETWEEN` or `NOT BETWEEN` when it did not hold two values, or with an operator that takes no list, such as `where('a', '=', [1])`. An empty array compiled to `()`, which ClickHouse rejects. `GLOBAL IN` and `GLOBAL NOT IN` now take a list like `IN`: `where('a', 'GLOBAL IN', [1, 2])` compiles to `` `a` GLOBAL IN (1, 2) ``. The other arrays throw an `InvalidArgumentException` when the condition is added. `BETWEEN` and `NOT BETWEEN` take the first two values in order, whatever their keys, as Laravel does: an array with string keys, such as `['from' => 1, 'to' => 2]`, compiles to `` `a` BETWEEN 1 AND 2 `` instead of raising `Undefined array key 0`, a third value is ignored, and a list of fewer than two values throws `The BETWEEN operator takes two values, the lower and the upper bound, but the array has 1.` A `null` bound is written as `NULL`, as Laravel binds it, so `[null, 5]` compiles to `` `a` BETWEEN NULL AND 5 ``, which matches no row, where 3.0.0 compiled `` `a` BETWEEN AND 5 ``. `whereBetween()`, `orWhereBetween()`, `whereNotBetween()`, `orWhereNotBetween()`, their `preWhere` and `having` variants and the `BetweenColumns` methods read their list the same way. They used `$values[0]` and `$values[1]`, so `whereBetween('a', ['from' => 1, 'to' => 2])` raised `Undefined array key 0`, an `ErrorException` in a Laravel app, and compiled `` `a` BETWEEN AND ``.
- `count()`, and with it the total of `paginate()`, replaced the columns of the query with `count()`. For a query with `UNION ALL` it therefore returned the count of the first query or a value from another query's rows, which varied from run to run. For a query with `GROUP BY` it returned the rows of one group, and with `HAVING` on an alias it failed. A query that selected an aggregate, `arrayJoin()` or a `DISTINCT` column counted the matching rows of the table instead of the rows the query returns, and an alias used in a condition, as in `select('id as x')->where('x', 3)`, failed with `UNKNOWN_IDENTIFIER`. The count also left out the `ORDER BY`, so it missed the rows that `orderByRaw()` adds with `WITH FILL` or multiplies with `arrayJoin()`: `select('id')->where('id', 999)->orderByRaw('id WITH FILL FROM 0 TO 3')->count()` returned `0`, though the query returns three rows. Without the `ORDER BY`, the where conditions of the count also read the table's column instead of an alias that an `ORDER BY` entry defines with `AS`: for the `oa` table of the Data safety entry above, `select('a')->where('b', '<', 5)->orderBy('a as b')` returns three rows, but its `count()` and the total of `paginate()` returned `1`. A query with set operations, `GROUP BY`, `HAVING`, `LIMIT BY`, a selected column that is not a plain column name, such as an expression, a `DISTINCT` column, an alias or a `withAlias()` name, or an `ORDER BY` entry that can add or multiply rows, which is `orderBy()` on a `withAlias()` name or `orderByRaw()` with `WITH FILL`, `arrayJoin` or a `withAlias()` name, is now counted in a subquery, ``SELECT count() AS `count` FROM (<query>)``, without its `LIMIT` and `OFFSET`. So is a query with an `ORDER BY` entry that defines an alias, which `delete()` and `update()` refuse (see Changed), and the subquery keeps that entry: ``SELECT count() AS `count` FROM (SELECT `a` FROM `oa` WHERE `b` < 5 ORDER BY `a` AS `b` ASC)``. So, too, is a query with an `ORDER BY` entry whose raw SQL has `LIMIT`, `LIMIT ... BY`, `OFFSET` or `FETCH` outside parentheses and quotes, which ClickHouse reads as clauses of the query: for a table `lb` with the rows `(1, 'g1')`, `(2, 'g1')` and `(3, 'g2')`, `select('id', 'grp')->orderByRaw('id DESC LIMIT 1 BY grp')` returns two rows, but its `count()` and the total of `paginate()` returned `3`; the count now sends ``SELECT count() AS `count` FROM (SELECT `id`, `grp` FROM `lb` ORDER BY id DESC LIMIT 1 BY grp)`` and returns `2`. Such a limit is counted, unlike `limit()` and `offset()`. Other `ORDER BY` entries only sort the rows, and the count still leaves them out, unless an entry adds rows with `WITH FILL` or limits them as above: the entries before a `WITH FILL` entry decide the groups in which ClickHouse adds the rows, and every entry decides which rows a limit keeps, and with `WITH TIES` how many, so the subquery then keeps the whole `ORDER BY`, and `select('grp', 'x')->orderBy('grp')->orderByRaw('x WITH FILL')->count()` sends ``SELECT count() AS `count` FROM (SELECT `grp`, `x` FROM `wf` ORDER BY `grp` ASC, x WITH FILL)``, which counts the rows that `get()` returns. So, too, is a query whose `ORDER BY` raw SQL adds a set operation with `UNION`, `INTERSECT` or `EXCEPT`: for the table `g` with the rows `(1, 10)`, `(2, 20)`, `(3, 30)` and `(10, 1)`, `where('a', '<', 5)->orderByRaw('a EXCEPT SELECT * FROM g WHERE b = 20')` returns two rows, and its count now sends ``SELECT count() AS `count` FROM (SELECT * FROM `g` WHERE `a` < 5 ORDER BY a EXCEPT SELECT * FROM g WHERE b = 20)`` and returns `2`. The raw SQL given to a `Column` function of an `ORDER BY` entry counts as SQL of the entry: for the `oa` table, `select('a')->where('b', '<', 5)->orderBy(fn (Column $column) => $column->name('a')->plus(raw('0 AS b')))` returns three rows, and its count sends ``SELECT count() AS `count` FROM (SELECT `a` FROM `oa` WHERE `b` < 5 ORDER BY `a` + 0 AS b ASC)`` and returns `3`, where it returned `1`. When the query uses `INTERSECT` or `EXCEPT`, or reads rows from a query that does, in `from()`, a join, or a `withExpression()` or `withRecursiveExpression()` given a builder or a closure, at any depth, `WHERE NOT ignore(*)` makes the count read every column: `DB::connection('clickhouse')->table($a->except($b))->count()` sends ``SELECT count() as `count` FROM (<a> EXCEPT <b>) WHERE NOT ignore(*)``. In a set operation, the `LIMIT` and `OFFSET` belong to the first query, and the subquery keeps them, with the `ORDER BY` that decides which rows they keep, so the count matches `get()`: `$a->orderBy('id')->limit(1)->unionAll($b)->count()` sends ``SELECT count() AS `count` FROM (<a> ORDER BY `id` ASC LIMIT 1 UNION ALL <b>)``. A grouped query without rows now counts as `0` without a warning; before, `count()` raised `Undefined array key 0`. As with `exists()`, settings that act on the result are not supported: with an `offset` setting, `count()` and the total of `paginate()` return `0`, where 3.0.0 raised `Undefined array key 0`, and `additional_result_filter` fails with `UNKNOWN_IDENTIFIER`. `paginate()`, `simplePaginate()` and `chunk()` read the whole set operation (see below), and the aggregates read the rows as `count()` counts them (see Changed). With `fix_default_query_builder` set to `false`, Laravel's query builder counts such queries in a sub-query of its own (see Changed).
- `format()` threw an `UnexpectedValueException` for a format name with lower-case letters, such as `format('JSONEachRow')` (`Value 'JSONEACHROW' is not part of the enum ...`), because it upper-cased the name; only `CSV`, `JSON`, `TSKV`, `TSV` and `XML` worked. It now takes a name in any letter case and writes it as ClickHouse spells it: `format('jsoneachrow')` and `format('JSONEachRow')` compile to `FORMAT JSONEachRow`, and `get()->rawData()` returns the rows as JSON lines. `format('json')`, `format('csv')` and `format('tsv')` compile as before. An unknown name still throws, now with the name as given: `Value 'jsonl' is not part of the enum Oralunal\LaravelClickHouse\ClickhouseBuilder\Query\Enums\Format`. `get()` reads the output in the format that the query names, so `rawData()` returns the text of `XML`, `Values`, a `Pretty` format and the others: `format('XML')->get()->rawData()` starts with `<?xml`, where 3.0.0 failed with a syntax error, `... FORMAT XML FORMAT JSON`, because the smi2 client added `FORMAT JSON`. `rows()` throws ``Can`t find meta`` for a format without meta data, such as `CSV`, `XML`, `JSONEachRow` or `JSONCompactEachRow`. The `rawData()` of `JSONCompactEachRow`, and of the other formats with one JSON value per line, holds the lines: `format('JSONCompactEachRow')->get()->rawData()` returns `"[1]\n[2]\n[3]\n"`.
- On PHP 8.5, a `NAN` value in `where()`, `preWhere()`, `having()`, their variants or `update()`, and a `NAN` item of an `InsertArray::TYPE_DECIMAL`, threw `ErrorException: unexpected NAN value was coerced to string`. It is now written as `nan`, and `INF` and `-INF` as `inf` and `-inf`: `where('f', NAN)->orWhereIn('f', [INF, -INF])` compiles to ``WHERE `f` = nan OR `f` IN (inf, -inf)``, and `new InsertArray([NAN, INF], InsertArray::TYPE_DECIMAL)` inserts `[nan,inf]` into an `Array(Float64)` column. ClickHouse finds no value equal to NaN, so such a condition matches no row; use `whereRaw('isNaN(f)')`.

- On PHP 8.5, a `NAN` float in a model insert, through `insertAssoc()`, `insertBulk()`, `create()`, `save()` or a buffer, or in the `insert()` of the query builder, threw `ErrorException: unexpected NAN value was coerced to string`. `NAN`, `INF` and `-INF` are now written as `nan`, `inf` and `-inf`, also inside arrays, as in `[1.5,-inf,[0.3333333333333333]]`; 3.0.0 wrote `INF` and `-INF`, which ClickHouse stores the same.
- A model insert, or an `insert()` of the query builder, of the package's `Expression`, such as `new RawColumn('now()')`, or of Laravel's `DB::raw()`, threw `Error: Cannot access protected property ...::$value`, and so did a `Stringable` value object whose `value` property is private or protected. These expressions are now written as the SQL they hold, also inside arrays, as the smi2 client's `Raw` already was: `insertAssoc([['id' => 1, 's' => DB::raw("upper('x')")]])` stores `X`. Such a value object is written as its string.
- **Data loss:** The rows that `buffer()` collected on a model that uses the `HasBufferedInserts` trait again, and on its children, were not sent by `BaseModel::flushAllBuffers()` or by the automatic flush at the end of a request or script, so they were lost when the process ended. Every copy of the trait now registers its models in one registry, and these rows are flushed too (see Changed).
- **Data safety:** `Schema::createDatabase()`, `Schema::dropDatabaseIfExists()`, and the `DROP` statements of `Schema::dropAllTables()` and `Schema::dropAllViews()`, which `migrate:fresh` and `db:wipe` run, sent their statements to the nodes without the connection: they were not logged, fired no `QueryExecuted` event and no `beforeExecuting()` callback, and ran while the connection pretended. They now go through `Connection::statementOnEveryNode()`, so they are logged once, fire the event and the callbacks, and send nothing while pretending. They still reach every node; on a connection with a `cluster_name`, as one statement with `ON CLUSTER` (see Changed).
- With the `migrations` table on a ClickHouse connection and `fix_default_query_builder` on, the packaged default, `migrate:rollback`, with or without `--step`, `--batch` or `--pretend`, `migrate:refresh --step`, and the repository's `getLast()`, `getMigrations()` and `getMigrationsByBatch()` failed with `Call to undefined method ClickHouseDB\Statement::all()`, because Laravel's migration repository read the table with the package's query builder. The package now binds `Oralunal\LaravelClickHouse\ClickhouseMigrationRepository` as `migration.repository`, which reads the table with Laravel's query builder on a ClickHouse connection, whatever `fix_default_query_builder` says, as in `select max("batch") as "aggregate" from "migrations"` and `select * from "migrations" where "batch" = ? order by "migration" desc`, and returns the migrations as objects. Every migration command works, on the default connection and with `--database` (24.8, 26.3 and 26.8 checked) (see Changed).
- **Data safety:** `migrate:refresh`, and any migration command right after a rollback, could read a rolled-back migration as run and skip it, because Laravel's migration repository deleted its row with an `ALTER TABLE ... DELETE`, which ClickHouse runs in the background: on ClickHouse 24.8, `migrate:refresh` ran only the second of two migrations again, and the table of the first stayed dropped. The repository now deletes the row with `mutations_sync = 1`, so the delete returns once the active node has deleted it (see Changed).
- **Data safety:** With asynchronous inserts, the default of ClickHouse 26.3 and 26.8, and `wait_for_async_insert = 0` in the connection's `settings` or the user's profile, an insert returns before its rows are written. So the row that the migration repository logged, and the rows of the `migrations` table that `migrate` loads from a schema dump, could be missing when the next command read the table: a migration ran again, and `migrate` failed to load a dump with `TABLE_ALREADY_EXISTS`. The repository's insert now carries `async_insert = 0` (see Changed), and each `INSERT INTO <table> VALUES` of a dump is sent with `SETTINGS async_insert = 0` before `VALUES`, so that their rows are written when the call returns, whatever the settings say. An `INSERT` of the dump with `SETTINGS`, a `FORMAT` clause or a `SELECT` of its own is sent as it is. The dump file is unchanged, and a dump that 3.0.0 wrote loads the same way.

### Security

- `min()`, `max()`, `sum()`, `avg()`, `average()` and `aggregate()` on the query builder quote a string column as a column name, so a column taken from user input, as in `->max($request->metric)`, no longer adds SQL to the query or reads other tables. This is **Breaking** for SQL passed as a string (see Changed).
- `update()` wrote each column name between backticks without escaping it. A column name taken from user input, such as a key of `$request->all()`, could therefore end the identifier early and add SQL to the statement, for example to change other columns or every row of the table. `update()` now quotes each name as one identifier and doubles its backticks and backslashes: ``update(['we`ird' => 'x'])`` sends ```UPDATE `we``ird` = 'x'```, where 3.0.0 sent ``UPDATE `we`ird` = 'x'``, which ClickHouse rejects. Plain names, and Nested names such as `n.a`, are written as before.
- The inserts passed the column names to the smi2 client, which writes each name between backticks without escaping it: `insert()` on the query builder, and `insertAssoc()`, `insertBulk()`, `prepareAndInsertAssoc()`, `create()`, `save()` and `flushBuffer()` on a model. A column name taken from user input, such as a key of `$request->all()`, could therefore end the identifier early and add SQL to the statement. The inserts now double the backticks and backslashes of each name, so it stays one identifier, as in `update()`. A name such as ``tick`name`` or `ends\`, which failed with a syntax error, now reaches its column. Plain names, and Nested names such as `n.a`, are sent as before. `prepareAndInsert()` and `prepareAndInsertBulk()` escape the names too (see Fixed).
- `InsertArray` wrote its string items into the `INSERT` without escaping them: the default `InsertArray::TYPE_STRING` escaped nothing, and `TYPE_STRING_ESCAPE` escaped single quotes but not backslashes. A single quote in an item therefore ended the string early, so `new InsertArray(["O'Brien"])` failed with a syntax error, and an item taken from user input could add rows to the `INSERT`. An item that ended with a backslash failed too, and a backslash sequence was read as an escape, so `C:\temp` was stored with a tab. Both types now escape the backslashes and single quotes of every item, so each item is stored as given. An item that you escaped by hand is now escaped twice: `"O\\'Brien"` stores `O\'Brien`, where 3.0.0 stored `O'Brien`. Items without a quote or a backslash are written as before.
- `addSelectDict()`, `whereDict()` and `orWhereDict()` wrote the dictionary and attribute names between single quotes, and the alias between backticks, without escaping them. A quote, a backslash or a backtick in a name changed where the string or the identifier ended, so the query failed with a syntax error, and a name taken from user input could add SQL to it. The dictionary and attribute names are now escaped string literals, and the alias, which defaults to the attribute name, is one identifier with its backticks and backslashes doubled: `addSelectDict("it's", 'name', raw('id'))` adds `` dictGetString('it\'s', 'name', id) as `name` ``, where 3.0.0 wrote `'it's'`. With an attribute name such as `a.b` or `x as y`, `whereDict()` and `orWhereDict()` split the name in their condition, so it did not read the alias they select: `whereDict('dd', 'a.b', raw('id'), 'w2')` compiled to ``WHERE `a`.`b` = 'w2'``, which failed with `UNKNOWN_IDENTIFIER` or read the table's own `` `a`.`b` ``, and `x as y` failed with a syntax error. The condition now reads the alias: ``WHERE `a.b` = 'w2'``. Plain names are written as before.
- With `fix_default_query_builder` set to `false`, Laravel's query builder handed its bindings to the smi2 client, which wrote a `Stringable` value without quotes and replaced `:0`, `{0}` and the like anywhere in the SQL, string literals and names included. `where('id', Str::of('0 or 1 = 1'))` sent `"id" = 0 or 1 = 1` and matched every row; it now sends `"id" = '0 or 1 = 1'`. With 41 bindings, as in `whereIn('id', range(100, 140))->orWhereRaw("name = 'a:30'")`, the literal became `'a130'`, and `update(['{0}' => 'ABC'])` sent `update "ABC" = 'ABC'`; both are now sent as written. Raw SQL with named bindings, `:name` or `{name}`, still goes to the smi2 client, but the bindings are made safe first: a `Stringable` value, such as `Str::of("x'y")`, is quoted, where 3.0.0 wrote it without quotes; `false` is `0`, where 3.0.0 wrote nothing; and a backed enum is its quoted value, a pure enum its quoted name, `DB::raw()` its SQL, a `DateTimeInterface` its text and `NAN` `nan`, where 3.0.0 failed or wrote the value without quotes. `null` still leaves the placeholder in place, a collection is still sent as its JSON text, and a float still has 14 significant digits.
- `BaseModel::optimize()` wrote its partition between single quotes without escaping it, so `optimize(true, "a'b")` failed with a syntax error, a backslash was read as an escape, and a value taken from user input could add SQL to the statement. It now writes the partition as `delete()` writes `IN PARTITION`: a string as an escaped string literal, `PARTITION 'a\'b'`, an integer as a number, `PARTITION 202401`, and the package's `Expression` or a `DB::raw()` as the SQL it holds, `PARTITION ID '202401'` for `new RawColumn("ID '202401'")` (see Changed).

## [3.0.0] - 2026-10-08

3.0 renames the package and its namespace. Nothing else changes for your code. The quickest way to upgrade is `/lc-upgrade-2x-to-3x`; see [UPGRADE.md](UPGRADE.md).

### Changed

- **Breaking:** The package is now published as `oralunal/laravel-clickhouse`, and the GitHub repository is `oralunal/laravel-clickhouse`. 2.0.2 is the last release of `oralunal/phpclickhouse-laravel`; that package is abandoned and its existing releases stay installable. `oralunal/laravel-clickhouse` conflicts with it, so Composer never installs both.
- **Breaking:** The namespace moves from `PhpClickHouseLaravel\` to `Oralunal\LaravelClickHouse\`, including the bundled `ClickhouseBuilder`, `ClickhouseSchemaBuilder` and `Enum` and the `raw()`, `tp()` and `array_flatten()` helpers. Class names below the namespace, configuration, the generated SQL and the behavior are unchanged. Values serialized with the 2.x class names, such as cached or queued `RawColumn` objects, cannot be unserialized by 3.0.

### Added

- The `lc-upgrade-2x-to-3x` coding-agent skill, installed by `php artisan clickhouse:install-skills`. Running `/lc-upgrade-2x-to-3x` makes the agent switch the package, rename the namespace across the application, refresh Laravel's caches and verify the result. `/plc-upgrade-1x-to-2x` stays for 1.x applications and now points to it as the next step.

### Fixed

- On a `cluster` connection, `Migration::createMergeTree()` created a table that was not replicated when the callback set the engine by name, for example `->engine(Engine::REPLACING_MERGE_TREE, 'version')`. The table became `ReplacingMergeTree` instead of `ReplicatedReplacingMergeTree`, so its rows were not replicated between the nodes. Setting the engine by name now keeps the replication. An `Engine` instance passed to `engine()` is still used as given. Existing tables are not changed, but wherever the migration runs again (a fresh install, CI, `migrate:fresh`) it now creates the replicated table.

## [2.0.2] - 2026-10-08

### Fixed

- Parallel test runs (`php artisan test --parallel`, `pest --parallel`) no longer let one process drop the ClickHouse tables of another. Since 2.0.1, `migrate:fresh`, and with it `RefreshDatabase` and `LazilyRefreshDatabase`, also empties secondary ClickHouse connections. Every process used the same ClickHouse database, so tests failed at random with `TABLE_ALREADY_EXISTS` or `UNKNOWN_TABLE`. Now each process gets its own database on every secondary ClickHouse connection, named `<database>_test_<token>` like Laravel's per-process database for the default connection.
  - A process creates the database for its first test case that uses a database testing trait, and keeps using it for its other test cases.
  - `--recreate-databases` drops it before the run, `--drop-databases` drops it after the run, and `--without-databases` keeps the configured database.
  - Test runs without `--parallel` are unchanged.
- Parallel test runs with ClickHouse as the default connection failed in every database test with `Database <database>_test_<token> does not exist. (UNKNOWN_DATABASE)`. The ClickHouse schema builder now supports `Schema::createDatabase()` and `Schema::dropDatabaseIfExists()`. It also reports a failed `Schema::hasTable()` as an `Illuminate\Database\QueryException`, so Laravel creates the per-process database as it does for other drivers.

## [2.0.1] - 2026-10-08

2.0.1 completes the 2.0 release. 2.0.0 was tagged from an earlier commit, before the schema builder and the enum base class were bundled, and was only available for a few hours. If you are upgrading from 1.x, go straight to 2.0.1 and follow [UPGRADE.md](UPGRADE.md). Apart from Laravel, the only remaining dependency is `smi2/phpclickhouse`.

### Changed

- **Breaking:** The schema builder used by `Migration::createMergeTree()` now ships inside this package under the `PhpClickHouseLaravel\ClickhouseSchemaBuilder` namespace. It is copied from `glushkovds/php-clickhouse-schema-builder` 1.1.1, which is no longer installed. The DDL it generates is unchanged. Migrations that import `PhpClickHouseSchemaBuilder\Tables\MergeTree` or `PhpClickHouseSchemaBuilder\Expression` must switch to the new namespace.
- **Breaking:** The builder's enums (`Operator`, `Format`, `JoinType`, `JoinStrict`, `OrderDirection`) now extend `PhpClickHouseLaravel\Enum\Enum`, which is copied from `myclabs/php-enum` 1.8.5. They used to extend `MyCLabs\Enum\Enum`, and `myclabs/php-enum` is no longer installed. Their constants and methods are unchanged.
- **Behavior change:** if MySQL or PostgreSQL holds the `migrations` table, `migrate:fresh` now also empties the ClickHouse databases your migrations write to, along with any ClickHouse database that has a dump in `database/schema`. Before, it left them untouched. Migrations written with `CREATE TABLE IF NOT EXISTS` therefore kept their ClickHouse data across `migrate:fresh`; that data is now dropped. The command keeps its production confirmation.

### Added

- `php artisan clickhouse:install-skills` installs the package's coding-agent skills into every agent it finds in the project.
  - It detects agents from their project files (`.claude/`, `.cursor/`, `.github/copilot-instructions.md`, `AGENTS.md`, …).
  - It writes `SKILL.md` to each agent's skills directory.
  - `--agent=` chooses the agents explicitly.
  - The first skill is `plc-upgrade-1x-to-2x`. Running `/plc-upgrade-1x-to-2x` in Claude Code, Cursor, Copilot, Codex and the other agents makes the agent carry out this upgrade and verify it.
- `php artisan migrate:fresh` and `php artisan db:wipe` now work on ClickHouse connections. Previously they failed with `This database driver does not support dropping all tables`. `Schema::dropAllTables()` drops every table, materialized view, view and dictionary on every node, ordering the drops so that ClickHouse accepts them. Views are dropped too, so the dump and the migrations can recreate them. `Schema::dropAllViews()` drops only views and materialized views.
- Secondary ClickHouse connections now follow the connection that holds the `migrations` table. A ClickHouse connection is secondary when a migration in the migrator's paths targets it or when `database/schema` has a dump for it.
  - `schema:dump` also writes `database/schema/<connection>-schema.sql` for each secondary connection.
  - When `migrate` loads the primary dump, each empty secondary connection is loaded from its own dump. If a secondary has no dump, its migrations are marked as pending again and run.
  - `migrate:fresh` empties the secondary connections as well.
  - ClickHouse connections that no migration or dump refers to are never touched.

### Removed

- The `glushkovds/php-clickhouse-schema-builder` and `myclabs/php-enum` dependencies.

### Fixed

- `DB::connection('<name>')->table(...)` on a ClickHouse connection other than `clickhouse` ran its queries against the `clickhouse` connection. Models with a non-default `$connection` logged their queries there as well. Because of this, `migrate --database=<name>` read and wrote the wrong `migrations` table. Query builders are now bound to the connection that created them.

### Upgrade note

- From 1.x: see [UPGRADE.md](UPGRADE.md), or run `php artisan clickhouse:install-skills` and then `/plc-upgrade-1x-to-2x` in your coding agent.
- From 2.0.0: replace `PhpClickHouseSchemaBuilder\` with `PhpClickHouseLaravel\ClickhouseSchemaBuilder\` in your migrations. If your own code uses `myclabs/php-enum`, require it yourself.

## [2.0.0] - 2026-10-08

2.0.0 was tagged before the schema builder and the enum base class were bundled. If you are upgrading from 1.x, go straight to 2.0.1.

### Changed

- **Breaking:** The query builder now ships inside this package under the `PhpClickHouseLaravel\ClickhouseBuilder` namespace. It no longer comes from the `oralunal/clickhouse-builder` dependency, and the `Tinderbox\ClickhouseBuilder` namespace is gone. The SQL it generates is unchanged.
- **Breaking:** The helper functions `raw()`, `tp()` and `array_flatten()` are no longer global. They now live in the `PhpClickHouseLaravel\ClickhouseBuilder` namespace.

### Removed

- **Breaking:** The parts of the old builder that needed the `the-tinderbox/clickhouse-php-client` HTTP client are not included, and that client is no longer installed. This removes `BaseBuilder::addFile()`, `values()`, `getValues()` and `getFiles()`, the `into_memory_table()` and `file_from()` helpers, the client-based `Query\Builder`, and the old builder's Laravel integration. This package's own `Builder` never sent those files to ClickHouse, so these methods could not work here. `whereIn()`, `preWhereIn()`, `whereGlobalIn()` and `havingIn()` used to turn a string that matched a temporary file into a table reference. They now always treat a string as a value. Because no file could be added, that branch never ran.
- The old builder's auto-discovered `ClickhouseServiceProvider` no longer gets installed. It registered a second `clickhouse` database driver with its own `Connection` class. This package's driver only took effect because its provider happened to boot later.

### Fixed

- `Column::subQuery()` and `Column::getSubQuery()` declared the client-based `Query\Builder` as their return type. Building a column sub-query from this package's `Builder` therefore threw a `TypeError`. They now return `BaseBuilder`.

### Upgrade note

- Replace `Tinderbox\ClickhouseBuilder\` with `PhpClickHouseLaravel\ClickhouseBuilder\` in your `use` statements, for example `Query\Expression`, `Query\Enums\Operator` and `Query\TwoElementsLogicExpression`.
- If you called the global `raw()`, import it with `use function PhpClickHouseLaravel\ClickhouseBuilder\raw;`, or use `new RawColumn(...)` or `new Expression(...)` instead.
- If your app requires `oralunal/clickhouse-builder` directly, remove it. The bundled copy replaces it.

## [1.5.0] - 2026-10-08

### Added

- `php artisan schema:dump` now works on ClickHouse connections, including `--prune`, `--path` and `--without-migration-data`. Previously it failed with a `BadMethodCallException` because the connection had no schema state. The dump uses HTTP only, so no `clickhouse-client` binary is needed. It lists tables, dictionaries, views and materialized views in dependency order and appends the rows of the migrations table. References written as `<database>.<table>` lose the database prefix when they point at the connection's own database, so you can load the file into a database with a different name.
- `php artisan migrate` loads `database/schema/<connection>-schema.sql` into a ClickHouse database where no migrations have run yet, then runs only the newer migrations. On a `cluster` connection, the statements go to every node, the same way `Migration::write()` does. `Connection::getSchemaState()` exposes the same loader for apps where ClickHouse is not the default connection.

### Fixed

- `Schema::drop()` and `Schema::dropIfExists()` on a ClickHouse connection used to do nothing, without any error, because the schema grammar could not compile them. They now run `DROP TABLE` and `DROP TABLE IF EXISTS`. A migration whose `down()` relied on these calls now really drops the table.

## [1.4.0] - 2026-08-20

### Fixed

- A published `config/clickhouse.php` is now actually read. The service provider only ever loaded its own bundled copy, so `php artisan vendor:publish --tag=clickhouse-config` followed by editing the file silently did nothing — including the documented way to declare a second ClickHouse connection. Precedence is now `config/database.php` > published `config/clickhouse.php` > packaged defaults.
- `insertBulk()` no longer drops the cast for the first column. `array_search()` returns index `0` for it, which the truthiness check treated as "not found", so a `boolean` cast on the first column was skipped and the raw PHP value reached ClickHouse (typically failing with `Cannot parse string 'false' as UInt8`).
- `flushBuffer()` no longer throws `Fields not match` when rows were buffered one at a time carrying the same keys in different orders. Buffered rows are reordered to the first row's key order at flush time. A row whose key *set* differs is left untouched, so a genuinely mismatched buffer still fails loudly instead of shipping fabricated column values.

### Upgrade note

- If you published `config/clickhouse.php` before this release and edited it, those edits had no effect and may have been worked around elsewhere (for example in `.env` or `config/database.php`). They now take effect, ranking above the packaged defaults and below `config/database.php`. Review the published file before deploying.

### Documentation

- Corrected the derived table name (`MyTable` resolves to `my_tables`, not `my_table`), the events section (only `create()` fires `creating`/`created`; `save()` fires just `saved`), the `InsertArray` example (`insertAssoc()` takes `column => value` rows), and the `$tableSources` comment (`UPDATE` and `TRUNCATE` target it as well).
- Added the missing `PhpClickHouseSchemaBuilder` imports to the Schema Builder migration example, which fataled when copied as written.
- Documented the `cluster_name` connection key, which `Migration::createMergeTree()` reads to emit `ON CLUSTER` and which appeared in no documentation — including the fact that it requires `->ifNotExists()`, since migrations are dispatched to each node in turn and `ON CLUSTER` already creates the table everywhere on the first dispatch.

## [1.3.0] - 2026-08-20

### Changed

- Consolidated duplicated internal scaffolding into shared helpers; public API and generated SQL are unchanged:
  - `Builder`: `delete()`, `update()`, and `insert()` resolve their target table through one protected `getTableForWrites()` helper (previously three copies, one with a divergent string cast).
  - `BaseModel`: `where()` and `whereRaw()` build their entry query through a shared protected static `newSourcedQuery()` helper; `select()` deliberately keeps its previous behavior (no sources table attached).
  - `Migration::createMergeTree()` reads the database name and cluster settings from the resolved `Connection` instead of re-fetching them from the global `config()` repository.
  - `WithClient::getThisClient()` now routes through `resolveConnection()`, and the deprecated static `getClient()` delegates to `getThisClient()`. For subclasses that override `resolveConnection()` or `getThisClient()`, the override now consistently applies to every client acquisition; previously some internal paths bypassed it.

## [1.2.0] - 2026-05-07

### Added

- In-memory buffered inserts on `BaseModel`: `buffer()` accumulates rows per-model and `flushBuffer()` sends them to ClickHouse as a single `insertAssocBulk` HTTP request. The `$casts` pipeline used by `insertAssoc()` is reused, so cast behavior is identical. On flush failure the buffer is preserved so the caller can retry.
- Helper methods alongside the buffer API: `bufferCount()`, `getBufferedRows()`, `clearBuffer()`, and `BaseModel::flushAllBuffers()`.
- Auto-flush on script shutdown: the service provider registers a Laravel `terminating` callback plus a `register_shutdown_function` fallback for non-HTTP scripts. Errors during auto-flush are reported via `report()` rather than thrown.

### Changed

- Extracted the row-normalization + cast loop from `insertAssoc()` into a shared `prepareAssocRowsForInsert()` helper so manual and buffered inserts go through the same path. Public behavior of `insertAssoc()` is unchanged.

## [1.1.0] - 2026-04-17

- Unit-level test coverage for `QueryGrammar`, `SchemaGrammar`, and `Builder` SQL generation — these run without Docker / ClickHouse.
