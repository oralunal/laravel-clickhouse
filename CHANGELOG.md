# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

4.0.0 is a full cleanup. The package's own query builder, `BaseModel`, the `Migration` class and the helpers that went with them are removed without a deprecation phase. Laravel's query builder, with the ClickHouse clauses, is now the only query builder, the Eloquent model of the package is the only model, and migrations are Laravel's own. [UPGRADE.md](UPGRADE.md) and the upgrade skills (see Added) describe each step of the upgrade.

### Added

- A documentation site, [laravel-clickhouse.oralunal.com](https://laravel-clickhouse.oralunal.com), built with VitePress from `docs/` and published to GitHub Pages by the `docs` workflow. It covers every feature in short pages, written in ASD-STE100 Simplified Technical English: getting started, Eloquent models and inserts, the query builder, updates and deletions, the schema builder and migrations, raw SQL, sessions, parallel queries, clusters, tests, the ClickHouse versions and the coding-agent skills. The README is now a short overview with links to it, and the content of `docs/howto_run_local_test.md` and `docs/known_issues.md` moved to the site. The [API reference](https://laravel-clickhouse.oralunal.com/reference/api), which `composer docs:api` writes from the code, lists every public class, constant and method. A test fails when the reference does not agree with the code, or when no guide page names a public method that is not internal. The site also has the documentation of 1.x, 2.x and 3.x, from the README and the changelog of 1.5.0, 2.0.2 and 3.0.0, with a version menu. It shows 4.x by default.
- Coding-agent skills for the upgrade to 4.0, installed by `php artisan clickhouse:install-skills`, which also lists them: `/lc-upgrade-3x-to-4x` from `oralunal/laravel-clickhouse` 3.x, `/lc-upgrade-2x-to-4x` from `oralunal/phpclickhouse-laravel` 2.x and `/lc-upgrade-1x-to-4x` from 1.x, each straight to 4.x. Running one makes the agent update the dependency and rewrite the code that 4.0 removes: models that extend `BaseModel` become Eloquent models, the package's query builder calls become calls of Laravel's query builder, `Migration::write()` and `createMergeTree()` become Laravel migrations, and the removed helpers, enums and options get their replacements. The agent then reviews with the user the writes and migrations whose behavior changes, verifies the result and compares the test suite with its result before the upgrade, which the user keeps before updating the dependency or the agent gets from a copy of the commit before the update. A skill that finds the code of another version names the skill to run, and the 2.x skill sends 2.0.0 to the 1.x skill. The command warns when it replaces a skill directory whose files differ from the package's, installs once for an agent named twice with `--agent`, and tells the user to start a new session of the agent before running a skill. The upgrades from 2.x and 1.x first rename the package and the namespaces, as `/lc-upgrade-2x-to-3x` and `/plc-upgrade-1x-to-2x` did, and then follow `/lc-upgrade-3x-to-4x`. [UPGRADE.md](UPGRADE.md) describes the three upgrades by hand.
- `Oralunal\LaravelClickHouse\QueryBuilder`, Laravel's query builder on a ClickHouse connection. `DB::connection('clickhouse')->table()`, `Connection::query()` and the queries of Eloquent models return it, and its grammar, `QueryGrammar`, writes the ClickHouse clauses with the argument conventions of Laravel's methods:
  - `final()`, and `FINAL` as the third argument of `from()` and of `Connection::table()`: `DB::connection('clickhouse')->table('t', 'x', true)` compiles to `select * from "t" as "x" final`. A query on a sub-query with `final()` throws a `LogicException`. `sample(0.1, 0.5)` compiles to `sample 0.1 offset 0.5`.
  - `arrayJoin()`, `leftArrayJoin()`, `arrayJoinSub()` and `leftArrayJoinSub()`: `arrayJoin(['tag' => 'tags', 'scores'])` compiles to `array join "tags" as "tag", "scores"`.
  - The ClickHouse joins, each with the arguments of `join()` and a `Sub` form with those of `joinSub()`: `innerJoin()`, `anyInnerJoin()`, `allInnerJoin()`, `anyLeftJoin()`, `allLeftJoin()`, `anyRightJoin()`, `allRightJoin()`, `fullJoin()`, `semiLeftJoin()`, `semiRightJoin()`, `antiLeftJoin()`, `antiRightJoin()`, `asofJoin()` and `asofLeftJoin()`: `anyLeftJoin('u', 't.uid', '=', 'u.id')` compiles to `any left join "u" on "t"."uid" = "u"."id"`.
  - `preWhere()`, `preWhereRaw()`, `preWhereIn()`, `preWhereNotIn()`, `preWhereNull()`, `preWhereNotNull()`, `preWhereBetween()`, `preWhereNotBetween()` and their `or` forms, which take the arguments of the `where` methods, closures and sub-queries included: `preWhere('a', 1)->where('b', 2)` compiles to `prewhere "a" = ? where "b" = ?`. Every other where method of the builder has a `PREWHERE` form too, `preWhere<Method>()` and `orPreWhere<Method>()`, such as `preWhereColumn()`, `preWhereDate()`, `preWhereAny()` or `orPreWhereLike()`: `preWhereColumn('a', '<', 'b')->orPreWhereDate('d', '2024-01-02')` compiles to `prewhere "a" < "b" or toDate32("d") = ?`.
  - `whereGlobalIn()`, `whereGlobalNotIn()` and their `or` forms; `whereEmpty()`, `whereNotEmpty()`, `havingEmpty()`, `havingNotEmpty()` and their `or` forms, which compile to `empty("name")` and `notEmpty("name")`.
  - `limitBy(3, 'user_id')`, which compiles to `limit 3 by "user_id"`, and `limitByWithOffset()`.
  - `settings()`, which takes an array or a name and a value, and writes them after the settings of `timeout()`, `forceIndex()` and `ignoreIndex()`: `settings('max_threads', 4)` compiles to `settings max_threads=4`. Later calls add up: a later value for the same setting replaces the earlier one, and `null` removes a setting. Each value is written by its type: `true` and `false` as `1` and `0`, integers and floats as numbers, strings as quoted strings with `\` and `'` escaped, a backed enum as its value, another `Stringable` object, such as `Str::of()` or a Carbon date, as a quoted string, and `DB::raw()` as its SQL. A setting name that is not a plain identifier (`[A-Za-z_][A-Za-z0-9_]*`), or a value of another type such as an array or a collection, throws an `InvalidArgumentException` when the query is compiled. ClickHouse rejects `SETTINGS` after the last parenthesized query of a union, so a union with settings is selected from: `select * from ((...) union all (...)) settings max_threads=1`.
  - `withExpression()`, `withRecursiveExpression()` and `withAlias()`, which compile to a `WITH` clause; `intersect()`, `intersectDistinct()`, `except()`, `exceptDistinct()` and `unionDistinct()`.
  - For the mutations: `onCluster()` and `withoutOnCluster()`; `delete($id = null, ?bool $lightweight = null, $partition = null)` and `update(array $values, $partition = null)`; and `truncate()`. See the entries below.
- Lightweight deletes. `delete(lightweight: true)` sends a lightweight `delete from "t" where ...` instead of `alter table "t" delete where ...`. ClickHouse hides the deleted rows before the call returns, so the next select no longer sees them. `ALTER TABLE ... DELETE` only queues a mutation that rewrites the data parts in the background. `delete(lightweight: false)` sends `ALTER TABLE ... DELETE`. The Eloquent builder takes the option as its first argument: `Event::where('user_id', 1)->delete(true)`. Lightweight deletes need a MergeTree-family table; ClickHouse rejects them on other engines, such as `Memory`, and on a table with projections unless the `lightweight_mutation_projection_mode` setting is `drop` (24.10 also accepts `rebuild`). On 24.8 it is a query setting: give it with `settings()` of the delete, or in the connection's `settings`. From 24.9 it is a table setting, which you set with `ALTER TABLE my_table MODIFY SETTING lightweight_mutation_projection_mode = 'drop'`.
- `settings()` of a `delete()` or an `update()` goes after the mutation, for the settings that change how it runs or how long the call waits for it: `where('id', 1)->settings('mutations_sync', 2)->update(['v' => 'x'])` sends `alter table "t" update "v" = 'x' where "id" = 1 settings mutations_sync=2`, and returns when the mutation is done. `QueryGrammar::MUTATION_SETTINGS` lists them, such as `mutations_sync`, `lightweight_deletes_sync`, `lightweight_mutation_projection_mode`, `log_comment` and `max_query_size`. The package refuses every other setting, such as `max_threads`, and names it in the message: ClickHouse (24.8 and 26.8 checked) ignores the settings that change the rows that a select reads in a mutation, such as `limit`, `offset` and `additional_table_filters`, and the mutation then changed every row that the conditions match.
- The `use_lightweight_delete` connection option (`CLICKHOUSE_USE_LIGHTWEIGHT_DELETE` in `.env`) decides what `delete()` sends when you do not give `$lightweight`. It defaults to `false`, so `delete()` sends `ALTER TABLE ... DELETE`.
- `delete()` and `update()` take a partition and add `IN PARTITION` to the statement, so the mutation only touches that partition: `delete(lightweight: false, partition: 202401)` sends `alter table "t" delete in partition 202401 where ...`, and `update(['v' => 'x'], '202401')` sends `alter table "t" update "v" = 'x' in partition '202401' where ...`. An integer is sent as a number, a string as an escaped string literal, and `DB::raw("ID '202401'")` as written. A lightweight delete in a partition (`DELETE FROM ... IN PARTITION`) needs ClickHouse 24.9 or later; older servers, 24.8 included, reject it with a syntax error.
- `optimize(bool $final = false, $partition = null): bool` on the query builder and the Eloquent builder, and the static `Model::optimize()`, send `OPTIMIZE TABLE`: `Event::optimize(true, 202401)` sends `optimize table "events" partition 202401 final`. The partition is written as `delete()` writes it, and `ON CLUSTER` follows `onCluster()` and the `use_on_cluster` option.
- `getStatement(Format|string|null $format = null)` on the query builder and the Eloquent builder runs the query and returns the smi2 `Statement` of its result, in the given format or in JSON: `DB::connection('clickhouse')->table('t')->getStatement('CSV')->rawData()` sends `select * from "t" format CSV` and returns the CSV text. `rawData()` gives the body of a text format, such as `CSV`, `Pretty` or `XML`, and the decoded document of a JSON format, and `totals()` and `extremes()` read a JSON result. A format name of the `Format` enum is matched in any letter case, and any other name must be a plain word, such as `TSVRaw`, or an `InvalidArgumentException` is thrown.
- `Connection::selectStatement(string $query, array $bindings = [])` runs SQL with any `FORMAT` clause and returns the smi2 `Statement` of its result, read in the format that the clause names: `DB::connection('clickhouse')->selectStatement('SELECT id FROM t FORMAT XML')->rawData()` returns the XML text. The bindings are written into the SQL as `select()` writes them, the query is logged once, an error of ClickHouse is thrown when the query runs, and while the connection pretends nothing is sent and the statement is empty.
- `insert()` of the query builder takes a format as its second argument, and the `insert_format` connection option (`CLICKHOUSE_INSERT_FORMAT`) sets the format of the other inserts: `Values`, Laravel's `insert into ... values`, or `JSONEachRow`, one JSON object per row. `DB::connection('clickhouse')->table('lqb')->insert([['id' => 1, 'name' => 'a', 'tags' => ['x']]], 'JSONEachRow')` sends `insert into "lqb" ("id", "name", "tags") format JSONEachRow` with the rows in the body of the request, and the query log lists it once, without bindings. Without the argument, `insert()` and `insertGetId()`, and with them Eloquent's `insert()`, `create()` and `save()` and the buffers of models, follow the connection's `insert_format`, `Values` by default. Both take `Values` or `JSONEachRow` in any letter case, or a `Format` case, and another format throws `insert() takes the format 'Values' or 'JSONEachRow', [CSV] given.` before anything is sent. `Connection::getInsertFormat()` returns the format of the connection.
  - The `INSERT` goes in the URL and the rows in the body of the request, so the smi2 client never replaces placeholders such as `:name` in the data, a retry sends every row again, and an error message names the `INSERT` without the data. Every row needs the keys of the first row, in any order, as in `Values` (see Changed), or `QueryException::insertKeysDiffer()` is thrown before anything is sent: `Cannot insert the rows as JSONEachRow: the row at index 1 lacks the keys [some_param]. ...`.
  - ClickHouse reads some values otherwise than in `Values` (24.8 checked). `true` goes into a `UInt8` column as `1`, an array with keys into a `Map` column, a list such as `[1, 'a']` into a `Tuple(UInt8, String)` column, and a pure enum as its name. A date with a time for a `Date` column, a float with a fraction, such as `2.5`, for an integer column, and `[]` for a `Map` column fail; pass `$date->format('Y-m-d')`, `(int)` or `round()`, and `new \stdClass()`. A string that is not valid UTF-8 and raw SQL, which `Values` takes, throw an `InvalidArgumentException` before anything is sent.
- `insertFiles($paths, Format|string $format = Format::Csv, array $columns = [])` on the query builder and the Eloquent builder inserts the rows of files in an input format into the table of the query, one `INSERT` per file with the file as its body, through the smi2 client's `insertBatchFiles()`: ``DB::connection('clickhouse')->table('my_table')->insertFiles('/data/a.csv', 'csvwithnames', ['id', 'we`ird'])`` sends ``INSERT INTO "my_table" ( "id","we`ird" ) FORMAT CSVWithNames``. Each column name is quoted as one identifier, where `insertBatchFiles()` writes the names as given. The format is matched in any letter case against `TabSeparated`, `TabSeparatedWithNames`, `CSV`, `CSVWithNames`, `JSONEachRow`, `CSVWithNamesAndTypes` and `TSVWithNamesAndTypes`, and any other format throws an `InvalidArgumentException` before anything is sent. A path that is not a readable file throws an `Oralunal\LaravelClickHouse\Exceptions\QueryException`, `Cannot insert the file [/data/b.csv]: it is not a readable file. No file was sent.`, and so does a client that uses a ClickHouse session, both before any file is sent. The files are sent together, and the smi2 client throws for the first file that failed after every file was sent, so the other files may be inserted. Each file must be sent and inserted within the connection's `timeout_query`, and the connection's `retries` do not apply. `insertFiles()` returns the statement of each file, keyed by path, and logs each insert. While the connection pretends, it logs each insert and sends no file.
- JSON paths of Laravel's query builder, such as `where('payload->user->name', 'Ann')`, read a JSON document in a `String` column, as `json()` creates it, with ClickHouse's JSON functions, in conditions, `select()`, `orderBy()` and `groupBy()`: `JSONExtractString("payload", 'user', 'name')`, which gives a string without its quotes, and a number, a boolean, an object or an array as its JSON text. A comparison with an int or a float reads the value as `Nullable(Float64)`, also in `whereIn()` and `whereBetween()`, so that a value that is no number, such as `"large"`, is `NULL`, where a string compared with a number fails with `TYPE_MISMATCH` (24.8 checked). `true` and `false` read the value as `Nullable(Bool)`, and `whereNull()` writes `JSONType("payload", 'deleted') = 'Null'`, which holds for `null` and for a missing key. An array index counts from 0, as in Laravel: `payload->tags[0]` is `JSONExtractString("payload", 'tags', 1)`, and `[-1]` is the last element. A key is written as a string literal, so it can hold any character. `whereJsonContains()` and `whereJsonOverlaps()` write `hasAll()` and `hasAny()` of the two arrays, read as `Array(String)`, `Array(Float64)` or `Array(Bool)` when the values are all of one kind, and compared as their JSON text otherwise; an array with keys, a JSON object, throws an `InvalidArgumentException`. `whereJsonContainsKey()` writes `JSONHas()` and `whereJsonLength()` `JSONLength()`. `update(['payload->color' => 'green', 'payload->user->age' => 30])` merges the values of the paths of a column into its document with `jsonMergePatch()`, for the rows whose column holds a JSON object, and keeps the others, `''`, `NULL`, an array or text that is no JSON, on which `jsonMergePatch()` fails (26.3 checked) and the mutation would fail with it. An object as the value replaces the object at its path. An array index in a path of `update()`, raw SQL as its value, and an update that sets a column and a path of it throw an `Oralunal\LaravelClickHouse\Exceptions\QueryException` and send nothing, as does a JSON path as a column of an insert, in `Values` and `JSONEachRow`: `Cannot insert into the JSON path [payload->a]: an insert writes whole columns. ...` `virtualAsJson()` and `storedAsJson()` of the schema builder write `ALIAS` and `MATERIALIZED` `JSONExtract(payload, 'color', 'String')`, with the type of the column, where they threw a `RuntimeException`.
- `whereFullText()` writes `hasAllTokens("body", ?)`, which a text index speeds up (see below), or `hasAnyTokens()` with `['mode' => 'any']`, one for each column, joined with `or`; another mode throws an `InvalidArgumentException`. The tokens compare with their letter case. ClickHouse 26.3 and 26.8 have these functions, and 24.8 does not. Laravel's vector queries, `whereVectorSimilarTo()`, `whereVectorDistanceLessThan()`, `selectVectorDistance()` and `orderByVectorDistance()`, write `cosineDistance("embedding", CAST(? AS Array(Float32)))`, the cosine distance of pgvector, which a vector similarity index speeds up in an order with a limit. Laravel threw `Vector distance queries are only supported by Postgres and MariaDB.`
- `Oralunal\LaravelClickHouse\Eloquent\Model`, an Eloquent model of a ClickHouse table, as the model of laravel-clickhouse/laravel-clickhouse: Eloquent's relations, eager loads, timestamps, casts, events, observers and `find()` work, also with the models of other connections. Its key is not incrementing and is a string by default, its connection is `clickhouse`, and its queries use the query builder above. A model on a connection of another driver throws a `LogicException`. Its Eloquent builder, `Oralunal\LaravelClickHouse\Eloquent\Builder`, passes `$lightweight` and `$partition` from `delete()` and `forceDelete()`, and `$partition` from `update()`, to the query builder, and returns what the query builder returns from `optimize()`, `getStatement()` and `insertFiles()`. `save()` of an existing model sends an `ALTER TABLE ... UPDATE` mutation. A date cast follows the connection's `datetime_precision` unless the model sets `$dateFormat` (see Changed).
- Buffered inserts on the Eloquent model: `Event::buffer($rowOrRows)` keeps one row, or a list of rows, in the memory of the process (an array with an integer key is a list of rows, as in 3.0.0, also with keys such as those of `array_filter()`), and `Event::flushBuffer()` inserts them in one `INSERT`, in the connection's `insert_format`, and returns `false` when nothing is buffered. The package flushes every buffer at the end of the request and of the command. `flushAllBuffers(bool $silent = false)`, `bufferCount()`, `getBufferedRows()` and `clearBuffer()` complete the API. The rows are inserted as given, as `insert()` inserts them: casts and mutators do not apply. **Data safety:** `buffer()` refuses a row whose keys differ from those of the first row of the call or of the rows already buffered, before it buffers any row of the call, with an `Oralunal\LaravelClickHouse\Exceptions\QueryException`: `Cannot buffer the rows of the model [App\Models\Event]: the row at index 1 has the keys [id], and the buffer needs the keys [id, s]. Every buffered row of a model must have the same column keys, in any order, because the buffer is sent as one insert. Nothing was buffered.` The same keys in another order are buffered, and the rows buffered before and after the refused call are flushed as usual. When a flush fails, it throws and the rows stay buffered; with `silent: true`, `flushAllBuffers()` reports the failure and flushes the other models. While the connection pretends, `buffer()` logs the insert at once and sends nothing, and a flush logs the insert of the rows buffered before `pretend()` and keeps them buffered, so that the first flush after `pretend()` sends them once.
- Native enums: `Oralunal\LaravelClickHouse\Enums\Format`, the ClickHouse formats that the package names, with `Format::named()`, which returns the case of a name in any letter case or throws a `ValueError`, and `Format::tryNamed()`, which returns `null` instead; and `Oralunal\LaravelClickHouse\Enums\DateTimePrecision`, with the cases `Second` and `Microsecond`.
- `Oralunal\LaravelClickHouse\LiteralGrammar`, which writes PHP values as ClickHouse literals, as the connection writes bindings, `escape()` and the values of inserts: `compileLiteral()`, `compileStringLiteral()`, `quoteString()`, `quoteIdentifier()`, `escapeInsertColumns()`, `compileSettings()`, `formatDateTime()`, `hasSubSecondPart()`, `setDateTimePrecision()`, `getDateTimePrecision()`, `setLaravelGrammarResolver()` and `getLaravelExpressionValue()`. `Connection::newLiteralGrammar()` returns one that writes dates at the connection's `datetime_precision` and Laravel's database expressions through the grammar of the connection.
- Laravel's schema inspection methods work on ClickHouse connections. `Schema::getTables()`, `getTableListing()`, `getViews()`, `hasView()`, `getColumns()`, `getColumnListing()`, `getColumnType()`, `hasColumn()`, `hasColumns()`, `getIndexes()`, `getIndexListing()`, `hasIndex()`, `getForeignKeys()` and `hasForeignKey()` used to throw `This database driver does not support retrieving ...`. They read `system.tables`, `system.columns` and `system.data_skipping_indices` of the connection's database, or of the database you name.
  - `getTables()` leaves out views, materialized views with their inner tables, and dictionaries. `getViews()` lists views and materialized views. The `size` of a `Merge` table is `null`, because ClickHouse reports the bytes of its source tables for it.
  - Columns report the full ClickHouse type. A column is nullable when its type accepts `NULL`: `Nullable(...)`, `LowCardinality(Nullable(...))`, `Variant(...)`, `Dynamic`, or a `SimpleAggregateFunction` over one of them. `MATERIALIZED` columns are stored generated columns and `ALIAS` columns virtual ones.
  - Indexes are the primary key, named `primary`, and the data-skipping indices. Their columns are the elements of the key or index expression, such as `['id', 'intHash32(id)']`, without parentheses that enclose the whole expression: ClickHouse 26.8 prints the key of ``ORDER BY (`id`)`` as `(id)`, and its columns are `['id']` on every version. The `type` of the primary key is `null`, as on Laravel's SQLite driver, so `php artisan db:table` lists its attributes as `primary`, or `compound, primary` for a key of several columns. A data-skipping index has its type, such as `bloom_filter`.
  - `getForeignKeys()` returns an empty array, and `Schema::getCurrentSchemaName()` returns the connection's database instead of `null`.
- `php artisan db:show` and `php artisan db:table` work on ClickHouse connections. `db:show` failed with `Call to a member function getAttribute() on null`, because `Connection::getServerVersion()` read the version from PDO; it now runs `SELECT version()`. `Connection::getDriverTitle()` returns `ClickHouse`. `Connection::threadCount()`, which `db:show` prints as Open Connections, returns the number of client connections to the active node, the TCP, HTTP, MySQL and PostgreSQL connections that `system.metrics` counts, this one included; it returned `null`. `db:show --counts` counts the rows of every table and `--views` those of every view, so they fail on a table that ClickHouse cannot read, such as a `Kafka` or `Set` table, and on a parameterized view.
- Laravel's `DatabaseTruncation` testing trait works on ClickHouse connections. The trait wraps the truncation in `Schema::withoutForeignKeyConstraints()`, which threw a `BadMethodCallException`. ClickHouse has no foreign keys, so `disableForeignKeyConstraints()` and `enableForeignKeyConstraints()` now return `true` without sending a query. Every table that holds rows is truncated, except the migrations table.
  - Views, materialized views and dictionaries are left alone. A dictionary keeps the rows it has loaded until it is reloaded.
  - List three kinds of tables in `$exceptTables`. ClickHouse cannot read `Kafka`, `Set`, empty `File` and unreachable `URL` or `S3` tables, so they fail every test. It cannot truncate `Buffer`, `Merge`, `Null`, `URL`, `Kafka`, `GenerateRandom`, `MySQL` and `PostgreSQL` tables, or an `S3` table whose path has globs, so they fail as soon as they return a row. And `TRUNCATE` on an `S3` table deletes its object from the bucket.
  - On a connection with several nodes, only the active node is truncated, so a table that is not replicated keeps its rows on the other nodes, unless the connection sets the `use_on_cluster` option (see below), which truncates every node with `TRUNCATE TABLE ... ON CLUSTER`.
  - The [testing page](https://laravel-clickhouse.oralunal.com/advanced/testing) of the documentation shows how to also empty the inner table of a materialized view, the rows waiting in a `Buffer` table and a table that is not replicated, and how to reload a dictionary.
- `Schema::create()` on a ClickHouse connection creates the table that the blueprint declares: its columns with their modifiers, and the ClickHouse table clauses. In 3.0.0 it knew eight column types, threw a `BadMethodCallException` for the others, such as `uuid()`, `boolean()`, `decimal()` or `dateTime()`, and dropped every modifier (see Changed). The documentation page [Laravel's schema builder](https://laravel-clickhouse.oralunal.com/schema/schema-builder) lists the types and the rules.
  - The callback receives an `Oralunal\LaravelClickHouse\SchemaBlueprint`, which is Laravel's `Blueprint` with the table clauses `orderBy()`, `partitionBy()`, `sampleBy()`, `ttl()`, `settings()` and `ifNotExists()`, and the column types `array()`, `map()`, `ipv4()`, `ipv6()` and `date32()`. Laravel's `engine()`, `comment()` and `primary()` set the engine, the table comment and the sorting or primary key. A callback that type-hints Laravel's `Blueprint` keeps working. A blueprint resolver still decides the blueprint of the schema builder it is set on: after `$schema = Schema::connection('clickhouse')` and `$schema->blueprintResolver($resolver)`, `$schema->create()` passes the resolver's blueprint. The `Schema` facade gets a new schema builder for each call, so `Schema::blueprintResolver($resolver)` followed by `Schema::create()` still passes a `SchemaBlueprint`.
  - Column types: each integer type gets the ClickHouse type of its size and sign (see Changed). `char()`, `ulid()` and `foreignUlid()` give `FixedString(<length>)`, `float()` gives `Float64`, or `Float32` for a precision up to 24, `double()` `Float64`, `decimal()` `Decimal(<total>, <places>)`, `boolean()` `Bool`, `enum()` `Enum(...)`, `json()` and `jsonb()` `String`, and `date()` `Date`. `dateTime()` and `timestamp()` give `DateTime`, or `DateTime64(<precision>)` for a precision above 0, with the time zone of `->timezone()`. `year()` gives `UInt16`, `binary()` `String` or `FixedString(<length>)`, `uuid()` `UUID`, `ipAddress()` and `macAddress()` `String`, `geometry()` and `geography()` the geo type of their subtype, `vector()` `Array(Float32)`, and `rawColumn()` its type. `time()` and `timeTz()` give `Time` on a server that has it (see below). `set()` and `computed()` throw a `RuntimeException` (see Changed).
  - Column modifiers: `nullable()`, `default()`, `useCurrent()`, `storedAs()` (`MATERIALIZED`), `virtualAs()` (`ALIAS`), `storedAsJson()` and `virtualAsJson()` (see above) and `comment()`, and the ClickHouse modifiers `lowCardinality()`, `codec()`, `ttl()`, `ephemeral()` and `timezone()`, which `Oralunal\LaravelClickHouse\SchemaColumnDefinition` describes. A float default of a `Decimal` column is written as a string literal, `DEFAULT '19.99'`, because ClickHouse cuts `DEFAULT 19.99` off at the scale of the column and stores `19.98`.
  - An index with a ClickHouse index type, given as the third argument of `index()` or with `algorithm()`, goes into the column list with its `granularity()`: `index('url', null, 'bloom_filter(0.01)')->granularity(4)` adds ``INDEX `visits_url_index` `url` TYPE bloom_filter(0.01) GRANULARITY 4``. An index without a type sends nothing, unless the `default_index_type` option gives it one (see below).

Without a `cluster_name`, it sends its statement to the active node only and keeps the engine as given, as in 3.0.0.

- The `engine` connection option (`CLICKHOUSE_ENGINE`) sets the engine of the tables that `Schema::create()` creates without `$table->engine()`. With `'engine' => 'ReplacingMergeTree'`, `Schema::create('events', fn ($table) => $table->id())` sends ``CREATE TABLE `events` (`id` UInt64) ENGINE = ReplacingMergeTree ORDER BY (`id`)``. It defaults to `null`, which means `MergeTree()`, and a blank value counts as not set. Laravel's `migrations` table takes the option only when it is `MergeTree`, `ReplicatedMergeTree` or `SharedMergeTree` with its arguments alone, and `MergeTree()` otherwise, because another engine would merge or lose its rows (see Changed).
- `Schema::hasDictionary()` tells whether a dictionary exists, in the connection's database or in the database of a `<database>.<dictionary>` name. `hasTable()` is `false` for dictionaries now (see Changed).
- The `retry_on` connection option (`CLICKHOUSE_RETRY_ON`) decides which failed requests a connection with `retries` sends again. `reads`, the default, sends every failed read again, and a write only when it never reached the server: the connection was refused, the host name was not found, or the connect timeout ran out. A read is a request that the smi2 client sends with `readonly=2`, such as `select()` and the reads of the query builder; a write has `readonly=0`, such as an insert, a mutation or DDL. `any` sends every failed request again, as 3.0.0 did, and `unsent` only the requests that never reached the server. A write that timed out on the client may still run on the server, and a retry runs it again: on ClickHouse 24.8, with `retries` set to `2`, an `INSERT` that timed out on the client stored its rows three times with `any`, and once with `reads` and `unsent`. The option is read in any letter case, and `null` and `''` mean `reads`. Any other value throws an `InvalidArgumentException` when the connection is created, also with `retries` set to `0`: `The [retry_on] option of the ClickHouse connection must be 'reads', 'any' or 'unsent', [bogus] given.`
- `Connection::statementOnEveryNode()` sends a statement to every node of the connection, one after another: `DB::connection('clickhouse')->statementOnEveryNode('SYSTEM RELOAD DICTIONARY my_dictionary')`. It logs the statement once, sends nothing while the connection pretends, returns `true`, and throws at the first node that fails, after the nodes before it have run the statement. A migration sends raw SQL with it, as `Migration::write()` did.
- `Schema::table()` on a ClickHouse connection sends `ALTER TABLE` statements for the commands that sent nothing in 3.0.0 (see Changed), in the order of the calls:
  - The columns that it adds go into one statement, with the modifiers of `Schema::create()` and their position from `first()` or `after()`: ``ALTER TABLE `visits` ADD COLUMN `referrer` Nullable(String) AFTER `id`, ADD COLUMN `country` LowCardinality(String)``. When the added columns go into several statements, `orderBy()` throws a `RuntimeException` before anything is sent.
  - `dropColumn()`, and `dropTimestamps()`, `dropSoftDeletes()`, `dropMorphs()` and the other drops of columns, send ``ALTER TABLE `visits` DROP COLUMN `legacy`, DROP COLUMN `old` ``. `rename()` and `Schema::rename()` send ``RENAME TABLE `visits` TO `visits_old` ``, and keep the database of a qualified name: ``RENAME TABLE `analytics`.`visits` TO `analytics`.`visits_old` ``. `comment()` sends ``ALTER TABLE `visits` MODIFY COMMENT 'Page visits'``, and `sampleBy()`, `ttl()` and `settings()` send `MODIFY SAMPLE BY`, `MODIFY TTL` and `MODIFY SETTING`; ClickHouse applies a new TTL to the rows that the table holds in a mutation that runs in the background. `partitionBy()` throws a `RuntimeException`, because ClickHouse cannot change the partition key of a table.
  - An index with a type sends ``ALTER TABLE `visits` ADD INDEX `visits_url_index` `url` TYPE bloom_filter(0.01) GRANULARITY 4``, and `->materialize()` adds ``ALTER TABLE `visits` MATERIALIZE INDEX `visits_url_index` `` to build it for the rows that the table holds, in a mutation that runs in the background; until that mutation is done, ClickHouse refuses to drop the index with `BAD_ARGUMENTS`. `dropIndex()` sends ``ALTER TABLE `visits` DROP INDEX IF EXISTS `visits_url_index` ``, so that a `down()` method can drop an index without a type, which was never created, as `dropMorphs()` does; a mistyped name is silent too. On a table outside the MergeTree family, such as a `Memory`, `Log` or `Distributed` table, which ClickHouse does not let have data-skipping indexes, `dropIndex()` and the index part of `dropMorphs()` send nothing. To know the engine, `Schema::table()` reads `system.tables` of the active node when it compiles `dropIndex()`, also under `toSql()` and `migrate --pretend`.

Without a `cluster_name`, the statements go to the active node only, and an `ALTER TABLE` of a `Replicated*MergeTree` table reaches the other replicas through Keeper.
- `change()` in `Schema::table()` changes a column, where 3.0.0 threw `RuntimeException: This database driver does not support modifying columns.` It sends `MODIFY COLUMN` with the new definition and, as on Laravel's other databases, removes what the new definition leaves out: for a column `source String DEFAULT 'web' COMMENT 'src'`, `$table->string('source')->nullable()->after('id')->renameTo('traffic_source')->change()` sends ``ALTER TABLE `visits` MODIFY COLUMN `source` REMOVE DEFAULT``, ``ALTER TABLE `visits` MODIFY COLUMN `source` REMOVE COMMENT``, ``ALTER TABLE `visits` MODIFY COLUMN `source` Nullable(String) AFTER `id` `` and ``ALTER TABLE `visits` RENAME COLUMN `source` TO `traffic_source` ``.
  - A `DEFAULT`, `MATERIALIZED` or `ALIAS` expression and a comment are removed, each in a statement of its own before the `MODIFY COLUMN`, unless `default()`, `useCurrent()`, `storedAs()`, `virtualAs()`, `ephemeral()` or `comment()` gives them again. The `CODEC` and the TTL of the column stay unless `codec()` or `ttl()` gives new ones, and an `EPHEMERAL` column stays `EPHEMERAL`, because ClickHouse 24.8 cannot remove it. `renameTo()` renames the column after the change.
  - To know what to remove, `change()` reads the type, the default and the comment of the column from `system.columns` of the active node when it compiles the statements, or, inside `session()`, those of a temporary table of that name, so `toSql()` and `migrate --pretend` reach the server.
  - **Data safety:** a new type rewrites the column in a mutation, and ClickHouse changes the type of the column first. When the mutation then fails to convert a value, the `ALTER` fails, and every later query that reads the column fails until the mutation is killed with `KILL MUTATION` and the type is changed back. `change()` therefore refuses, before anything of the blueprint is sent, to make a column that holds `NULL` values, at the top or in the elements of an array at any depth, a type that cannot hold them. It runs ``SELECT 1 FROM `visits` WHERE `referrer` IS NULL LIMIT 1 SETTINGS apply_deleted_mask = 0``, or, on a connection with a `cluster_name`, ``SELECT 1 FROM clusterAllReplicas('company_cluster', 'default', 'visits') WHERE `referrer` IS NULL LIMIT 1 SETTINGS apply_deleted_mask = 0``, which reads every host, within the connection's `timeout_query`, and throws a `RuntimeException`: ``The column [referrer] of the table [visits] holds NULL values, so its type cannot change from Nullable(String) to String: ClickHouse would fail to convert them in a mutation, and every later query that reads the column would fail until the mutation is killed. Replace the NULL values first, or keep the column nullable(). Rows removed by a lightweight DELETE count too until a merge rewrites their parts; ALTER TABLE `visits` APPLY DELETED MASK removes them.`` Maps, tuples and other values that cannot be converted, such as the text `'abc'` of a `String` column that becomes an `Int64`, are not checked.
  - The statements run one after another, so when the server refuses the `MODIFY COLUMN`, as it refuses a new type for a column of the sorting key with `ALTER_OF_COLUMN_IS_FORBIDDEN`, the `REMOVE` statements before it have run.

A value that is neither a string nor `null`, such as the `true` that `env()` makes of `true`, throws an `InvalidArgumentException` when the connection is created (see Changed). An index with a type of its own keeps it, and on a table outside the MergeTree family an index without a type sends nothing. In `Schema::table()`, the engine of the table is read from `system.tables` when the statement is compiled.
- `has()`, `whereHas()`, `doesntHave()`, `whereRelation()`, `whereHasMorph()` and their `or` forms on the Eloquent builder of the package check the relation with an `IN` sub-query, which ClickHouse 24.8 runs, where Laravel's correlated `EXISTS` fails with `UNSUPPORTED_METHOD`: `User::whereHas('posts')` sends `select * from "users" where "users"."id" in (select "posts"."user_id" from "posts")`. `doesntHave()` sends `("users"."id" not in (...) or "users"."id" is null)`, since a row whose key is `NULL` has no related row, and a count, as in `has('posts', '>=', 2)`, groups the sub-query by the related column, with `having count(*) >= 2`, or with `not in` when no related row at all satisfies the count, as with `'<', 2`. - `Schema::dropSync()` and `Schema::dropIfExistsSync()`, and `->sync()` after `drop()` or `dropIfExists()` in a blueprint, add `SYNC` to the statement: `Schema::dropSync('visits_old')` sends ``DROP TABLE `visits_old` SYNC``. `SYNC` waits until ClickHouse has removed the data and, for a replicated table, its replica in Keeper. ### Changed

- **Breaking:** `DB::connection('clickhouse')->table()`, `Connection::query()` and the queries of Eloquent models return `Oralunal\LaravelClickHouse\QueryBuilder`, a subclass of Laravel's `Illuminate\Database\Query\Builder` (see Added), and never the package's own query builder, which is removed (see Removed). It follows Laravel's API: `get()` returns a `Collection` of associative arrays, `first()` an associative array or `null`, `toSql()` shows `?` placeholders and `toRawSql()` the values, and names are written between double quotes, with lower-case keywords: `select * from "my_table" where "id" = ?`. Where the package's builder had its own behavior, the query builder now behaves as Laravel's, with these ClickHouse rules:
  - `count()` without a column, and the total of `paginate()`, count the rows that `get()` returns. A query with `groupBy()`, `distinct()`, `groupLimit()`, `limitBy()`, `arrayJoin()`, `withAlias()`, a select alias or expression, such as `selectRaw()` or `selectSub()`, or an order that defines an alias, calls `arrayJoin()`, adds rows with `WITH FILL`, or has `LIMIT`, `LIMIT ... BY`, `OFFSET`, `FETCH`, `UNION`, `INTERSECT` or `EXCEPT` in its raw SQL, is counted in a sub-query, without its `LIMIT` and `OFFSET`: `select('id as x')->where('x', 3)->count()` sends `select count(*) as "aggregate" from (select "id" as "x" from "my_table" where "x" = 3) as "aggregate_table"` and returns `1`. `groupBy('user_id')->count()` returns the number of groups, with or without a select list, `distinct()->select('user_id')->count()` the number of distinct rows, and `selectRaw('count() as c')->count()` returns `1`. A grouped query without a select list and with `having()` is counted the same way. `distinct('user_id')->count()`, which sends `count(distinct "user_id")`, `count($column)`, unions, other queries with `having()`, `limit()->count()` and plain queries are counted as Laravel counts them. A count in a sub-query evaluates the select list, so it can take longer than a count of the table.
  - `sum()`, `avg()`, `min()`, `max()` and `aggregate()` are Laravel's: they replace the select list with the aggregate and drop the order, so they aggregate the rows of the table that the conditions select, not the rows that a select list or an order with `WITH FILL` or a raw limit makes. A union is aggregated in a sub-query, as Laravel does, and keeps the order of its first query, which decides, with its limit, which rows that query returns: `$a->orderBy('x')->limit(1)->unionAll($b)->sum('x')` sends `select sum("x") as "aggregate" from ((select "x" from "a" order by "x" asc limit 1) union all (select "x" from "b")) as "temp_table"`. The package's builder also replaced the select list, but kept the order and the limit in the same query: `sum('x')` of `select('x')->orderBy('x')->limit(1)` sent `SELECT sum(x) AS aggregate FROM a ORDER BY x ASC LIMIT 1`, and of a union it replaced the select list of the first query only.
  - ClickHouse (24.8 checked) leaves the columns that an outer query does not read out of the queries that `INTERSECT` and `EXCEPT` compare, so a count or an `EXISTS` over them compared fewer columns than `get()` does: the count of an `EXCEPT` that returns two rows was `0`. `count()`, the other aggregates, `exists()` and `whereExists()` therefore read every column of such rows, in a `from()` sub-query, a join, a with expression, also one of the outer query that an `EXISTS` sub-query reads by its name, or the query itself: `fromSub($a->except($b), 's')->count()` sends `select count(*) as "aggregate" from ((...) except (...)) as "s" where not ignore(*)`, and `$a->except($b)->exists()` sends `select exists(select * from ((...) except (...)) as "exists_table" where not ignore(*)) as "exists"`. `NOT ignore(*)` is true for every row.
  - `exists()` sends Laravel's `select exists(...) as "exists"` and reads the only column of the row, whatever its name: without the analyzer (`enable_analyzer = 0`), ClickHouse 24.8 names that column `in(1, _subquery1)` for a query with a with expression or a join. A query that calls `arrayJoin()`, as `selectRaw()`, `withAlias()` or an order can, is selected from, `select exists(select * from (...) as "exists_table" where not ignore(*)) as "exists"`, also in `whereExists()`: ClickHouse 26.8, with the analyzer, answered `true` for such a query over an empty array.
  - `pluck()` reads each column by the name that ClickHouse gives it: a column of a joined table keeps its table name, so `select('t.id', 'u.s')->join(...)->pluck('u.s')` reads `u.s`, while a column of the query's own table loses its table name, as Laravel reads it.
  - `chunk()`, `paginate()`, `first()` and `value()` are Laravel's, so `chunk()` needs an order, and `first()` and the paginators leave their `LIMIT` on the builder they run on.
  - Laravel's operators are the operators: `where('id', 'IN', [1, 2])`, `where('id', 'BETWEEN', [1, 2])` and `where('comment', 'IS NULL', null)`, which the package's builder read as `IN`, `BETWEEN` and `IS NULL`, now compare the column with the text of the operator: `where "id" = 'IN'`. The package's builder threw an `UnexpectedValueException` for these operators in lower case. Use `whereIn()`, `whereBetween()` and `whereNull()`.
  - `where('id', [1, 2])`, without an operator, compares with the first value only, as in Laravel: `where "id" = 1`, without an error. The package's builder, and `BaseModel::where()`, read it as `IN (1, 2)`. A `delete()` or `update()` with such a condition changes fewer rows. Use `whereIn()`.

The message names the clauses and says to select the keys first: `Cannot delete with a query that uses JOIN: a ClickHouse DELETE only takes the where and prewhere conditions, so this clause would be ignored, and the delete could remove rows that the query does not select. Select the keys first, and delete by them instead: whereIn('id', $query->pluck('id')).` For `SETTINGS`, it names the refused settings. Laravel's `first()`, `value()`, `find()`, `sole()`, `chunk()`, `paginate()` and `simplePaginate()` leave a `LIMIT` on the builder they run on, so a `delete()` or `update()` on that builder afterwards throws as well, and for a `LIMIT` or an `OFFSET` the message adds that such methods leave a `LIMIT` on the query they run on. Laravel's `updateOrInsert()` throws when the row exists, because it adds `limit(1)` to the update, and the message of an update with a `LIMIT` on this path says so; in 3.0.0 that update failed with a syntax error. The prewhere conditions of a mutation join its where conditions, as in `alter table "t" delete where ("a" = ?) and ("b" = ?)`, because a mutation has no `PREWHERE`.
- **Behavior change:** The query builder writes a float with every digit, where 3.0.0 wrote the 14 significant digits of PHP's string conversion. This applies to its conditions, `update()` and `insert()`, to the `?` bindings of raw SQL and to `Connection::escape()`: `where('ratio', 1 / 3)` sends `"ratio" = 0.3333333333333333` instead of `"ratio" = 0.33333333333333`, `where('v', 0.1 + 0.2)` `"v" = 0.30000000000000004` instead of `"v" = 0.3`, and `whereIn('w', [0.1, 2.0])` `"w" in (0.1, 2.0)` instead of `"w" in (0.1, 2)`. A condition now finds a `Float64` value that was stored with every digit, such as `1/3`, which the 14 digits missed. A float computed in PHP is no longer rounded either, so it can miss a `Decimal` or integer value, and `update()` stores it cut off at the scale of the column, because ClickHouse reads the float as a `Float64` and cuts it off when it converts it: `4.35 * 100` is `434.99999999999994` in PHP, so `where('price', 4.35 * 100)` no longer matches a stored `435.00`, and `update(['price' => 4.35 * 100])` stores `434.99` in a `Decimal(10, 2)` column, where 3.0.0 stored `435.00`. `update(['cents' => 0.29 * 100])` stores `28` in an `Int32` column instead of `29`. In `update()`, rounding does not help a value with a fraction: `update(['price' => round(19.99, 2)])` stores `19.98`, as `update(['price' => 19.99])` did in 3.0.0 and still does. An insert stores the float `19.99` as `19.99`, because ClickHouse reads a number in the rows of an `INSERT ... VALUES` straight into the column's type, but a computed float is cut off at the scale of the column: `DB::table('t')->insert(['price' => 4.35 * 100, 'cents' => 0.29 * 100])` stores `434.99` in a `Decimal(10, 2)` column and `28` in an `Int32` column, where 3.0.0 stored `435.00` and `29`. - **Behavior change:** **Data safety:** `delete()` and `update()` refuse a condition that ClickHouse cannot run in a `SELECT`, before the mutation is sent. In 3.0.0, ClickHouse accepted such a mutation, such as one whose sub-query reads a column of the mutated table, as `whereExists(fn ($query) => $query->from('orders')->whereColumn('orders.user_id', 'users.id'))` on `users` does, and then failed it again and again, which held back every later mutation of the table until `KILL MUTATION`; a lightweight delete threw and left the same mutation. Now, when the condition holds `SELECT`, or `IN` followed by anything but a parenthesis, as in `whereIn('id', DB::raw('ids'))`, outside quotes, `explain plan select 1 from <table> <conditions>` runs first, with `settings use_index_for_in_with_subqueries = 0` on a line of its own, and an error of ClickHouse throws a `QueryException`, whose previous exception is that error: `Cannot delete with a where condition that ClickHouse cannot run: it refused the condition in a SELECT with UNSUPPORTED_METHOD. A sub-query that reads a column of the table of the delete, such as whereExists() with whereColumn() on that table, is such a condition: ClickHouse (24.8 checked) accepts the mutation and then fails it again and again, which blocks every later mutation of the table until KILL MUTATION. Nothing was sent. Select the keys first, and delete by them instead: whereIn('id', $query->pluck('id')).`
  - A table of the condition that does not exist is refused the same way, with `UNKNOWN_TABLE` or `UNKNOWN_IDENTIFIER`, and so is a condition of a user who may change the table but not read a table of the condition, with `ACCESS_DENIED`: delete by the keys, or grant `SELECT`. Inside `session()`, the check of a mutation of a table of the database runs outside the session, so a condition that reads a temporary table of the session is refused too (see Added).
  - The check is one more read-only request. It runs while the statement compiles, and is logged and fires `QueryExecuted`, as a `select()` does: `explain plan select 1 from "users" where "id" in (select "user_id" from "orders")` and `settings use_index_for_in_with_subqueries = 0` on the next line. ClickHouse does not run an `IN` sub-query for it, but runs a scalar sub-query, such as that of `where('id', fn ($query) => $query->selectRaw('max(id)'))`, once for the check and again for the mutation. Nothing is sent for it while the connection pretends, and a condition without such a sub-query or `IN` is left for ClickHouse to check when it gets the mutation.
  - ClickHouse 26.3 and 26.8 run the `EXPLAIN` of a correlated sub-query, and then refuse the mutation themselves, at once, with `UNKNOWN_IDENTIFIER` (`Missing columns: 'users.id' ...`) on 26.3 and `NOT_IMPLEMENTED` (`Correlated subqueries in mutation filter are not supported`) on 26.8, a `ClickHouseDB\Exception\DatabaseException`, and leave no mutation behind.
- **Behavior change:** **Data safety:** A lightweight delete, `delete(lightweight: true)`, or `delete()` on a connection with `use_lightweight_delete`, whose condition holds `UNION`, `INTERSECT` or `EXCEPT` outside quotes, as a `whereIn()` sub-query with `unionAll()` or a `whereExists()` over an `EXCEPT` writes it, throws a `QueryException` before anything is sent: `Cannot send a lightweight DELETE FROM whose where condition holds a sub-query with UNION, INTERSECT or EXCEPT: ClickHouse (24.8 checked) fails such a delete and leaves its mutation behind, which blocks every later mutation of the table until KILL MUTATION. Nothing was sent. Send ALTER TABLE ... DELETE with the same condition, with delete(lightweight: false) or the connection's statement(), ...`. In 3.0.0, ClickHouse 24.8 failed such a delete with `UNION mode UNION_DEFAULT must be normalized` and left a mutation that held back every later mutation of the table, and 26.3 does the same; 26.8 runs it. `delete(lightweight: false)` takes the same condition. Raw SQL with one of these words for another reason, such as `SELECT * EXCEPT (col)` in a `whereExists()` sub-query, is refused too.
- **Behavior change:** `select()`, `scalar()`, `selectOne()`, the query builder, `selectParallelly()` and the entries of `Parallel` throw an `Oralunal\LaravelClickHouse\Exceptions\QueryException`, which is a `ClickHouseDB\Exception\QueryException`, before anything is sent or logged, when the `FORMAT` clause of the query names a format other than `JSON`, `JSONStrings`, `JSONCompact` and `JSONCompactStrings`, which they still read rows from, in any letter case: `Cannot read rows from a query whose FORMAT clause names XML: select() and parallel queries read the rows of a JSON result (JSON, JSONStrings, JSONCompact, JSONCompactStrings). Leave the FORMAT clause out, or read the result with selectStatement($sql)->rawData().` `Connection::selectStatement()` and the query builder's `getStatement()` read a result in any format (see Added). In 3.0.0, these queries were sent: `XML`, `Pretty`, `Values` and `Null` failed with `SYNTAX_ERROR` (`... FORMAT XML FORMAT JSON`), `CSV`, `TSV` and `JSONEachRow` failed with ``Can`t find meta`` after the query ran, or returned no rows for an empty result, and `JSONCompactEachRow` returned no rows although rows matched. The `FORMAT` clause is the word `FORMAT` and a name at the end of the query, before `SETTINGS` and `;` only, outside string literals, quoted names, comments, heredocs and parentheses. A column, an alias or a table named `format`, as in `ORDER BY format DESC`, `WHERE format IN ('csv')` or `SELECT * FROM format(CSV, '1')`, is no `FORMAT` clause, and such a query runs as in 3.0.0. `cursor()`, which asks for `JSONEachRow` itself, refuses every `FORMAT` clause, `JSON` included (see Fixed).
- **Behavior change:** On a client that uses a ClickHouse session, as after the smi2 client's `useSession()`, a lightweight delete, a `delete()`, `update()`, `truncate()` or `optimize()` with `ON CLUSTER`, and, on a connection with a `cluster_name`, a schema statement with `ON CLUSTER`, of a table name that a temporary table of the session has, throw `QueryException::cannotReachTemporaryTable()` before anything is sent (see Added). In 3.0.0, such a statement changed the table of the database, on every node with `ON CLUSTER`, or failed with `UNKNOWN_TABLE`. Each such statement sends one `EXISTS TEMPORARY TABLE` first, and `delete()` and `update()` send the check of a condition with a sub-query outside the session.
- The package is tested on ClickHouse 24.8, 26.3 and 26.8. The documentation page [ClickHouse versions](https://laravel-clickhouse.oralunal.com/reference/clickhouse-versions) lists what 26.3 and 26.8 do otherwise than 24.8 with their default settings, such as 64-bit integers returned as JSON numbers from 25.8, asynchronous inserts, the parsing of dates with a sub-second part and the slower mutations of 26.8 on a server with little RAM, and the settings that bring back the behavior of 24.8.

### Fixed

- **Data safety:** `delete()` and `update()` used only the where conditions of the query and ignored the clauses that decide which rows it selects, so they changed rows that the query does not select. In 3.0.0, `where('field_two', '<', 0)->orderBy('created_at')->limit(2)->delete()` deleted every row with a negative `field_two`, and a join, `groupBy()`, `having()`, a union, a select alias, an `orderByRaw()` that calls `arrayJoin()` or has `LIMIT ... BY` in it, or an order that defines an alias, which ClickHouse lets the where conditions read, were ignored the same way: `where('id', '>', 0)->orderByRaw('ts desc limit 1 by user')->delete()` sent `alter table "t" delete where "id" > 0` and deleted the rows of every user, though the query selects one row of each. These queries now throw a `QueryException` (see Changed). To change the rows that such a query selects, select their keys first: `whereIn('id', $query->pluck('id'))->delete()`. The [documentation](https://laravel-clickhouse.oralunal.com/query-builder/writing-data#refused-clauses) explains when the query as a sub-query is not the same.
- `delete()` and `update()` without a where or prewhere condition sent a statement without a condition, or one ending in `WHERE `, which ClickHouse rejects. They now throw `Oralunal\LaravelClickHouse\Exceptions\QueryException` without sending anything. To remove every row, call `truncate()`; to update every row, add `whereRaw('1')`. Any condition counts, including the `1 = 1` of an empty `whereNotIn()` list (see Changed).
- `DB::connection('clickhouse')->table(...)->update([...])` sent Laravel's `update ... set ...`, which ClickHouse 24.8 rejects with a syntax error. It now sends `alter table ... update ...`, with an array or a collection value written as an array literal: `where('id', 1)->update(['tags' => ['a', 'b']])` sends `alter table "t" update "tags" = ['a', 'b'] where "id" = 1`. An associative array loses its keys, so write a `Map` with `DB::raw("map('k', 1)")`.
- `Schema::hasTable()` put the database and table names into the query without escaping them, so a name containing `'` or `\` caused a syntax error. They are now escaped.
- `Schema::hasTable('analytics.events')` looked for a table named `analytics.events` in the connection's database and returned `false`. It now looks for `events` in the `analytics` database, as Laravel's other drivers and the schema inspection methods above do. A name with a dot is read as `<database>.<table>`.
- On PHP 8.5, a `NAN` value in a condition, `update()`, an insert or a binding threw `ErrorException: unexpected NAN value was coerced to string`. It is now written as `nan`, and `INF` and `-INF` as `inf` and `-inf`, also inside arrays: `where('f', NAN)->orWhereIn('f', [INF, -INF])` sends `"f" = nan or "f" in (inf, -inf)`. ClickHouse finds no value equal to NaN, so such a condition matches no row; use `whereRaw('isNaN(f)')`.
- `Cluster::slideNode()` stayed on the current node when the next node did not answer, so on a connection with three or more nodes it never reached the nodes after one that was down. It now tries each node after the current one in turn, continues with the first node after the last one, and moves to the first node that answers. When no other node answers, it stays on the current node, as before.
- **Data safety:** `DB::connection('clickhouse')->pretend()` and `php artisan migrate --pretend` ran the statements of ClickHouse connections while they listed them as pretended: `pretend(fn ($connection) => $connection->statement('CREATE TABLE ...'))` created the table, an `ALTER TABLE ... DELETE` deleted rows, `Schema::create()` and `Schema::drop()` created and dropped tables, and the query builder changed data. A pretended query with a string binding failed with `Call to a member function quote() on null`. Now `select()`, `statement()`, `insert()`, `update()`, `delete()`, `affectingStatement()`, `unprepared()`, `cursor()` and `statementOnEveryNode()` send nothing while the connection pretends, and return what Laravel's drivers return: `select()` and `cursor()` give no rows, so `Schema::hasTable()` is `false`; `statement()`, `insert()` and `unprepared()` return `true`; and `affectingStatement()`, `update()` and `delete()` return `0`. The log lists each statement with its bindings written in, such as `ALTER TABLE my_table DELETE WHERE field_one = 'it\'s'`. So are the writes of models, the statements of `Schema::table()`, `Schema::createDatabase()` and `Schema::dropDatabaseIfExists()` (see below), and the JSONEachRow inserts, `truncate()`, `optimize()`, `insertFiles()` and `selectStatement()` of the query builder and the connection: a JSONEachRow insert is listed with its `insert ... format JSONEachRow` only. The rows of a JSONEachRow insert are encoded while pretending too, so a row that the insert would refuse, with raw SQL or a string that is not valid UTF-8, throws an `InvalidArgumentException`, and nothing is listed. The buffers of models keep their rows while pretending (see Added). The checks that `delete()` and `update()` send first, the `EXPLAIN` of a condition with a sub-query and the lookup of a session's temporary tables, are not sent, and `session()` sends its opening `SELECT 1`.
- `?` placeholders did not work on ClickHouse connections: `select()`, `statement()`, `insert()`, `update()`, `delete()` and `affectingStatement()` sent the `?` to ClickHouse, which failed with a syntax error, such as `Cannot parse expression of type UInt32 here: ?, ?, ...` for an `INSERT ... VALUES (?, ...)`. The connection now writes the bindings into the SQL as ClickHouse literals (see Changed): `DB::connection('clickhouse')->insert('INSERT INTO t (a, b, c) VALUES (?, ?, ?)', [1, 19.99, new DateTime('2024-01-02 03:04:05')])` sends `INSERT INTO t (a, b, c) VALUES (1, 19.99, '2024-01-02 03:04:05')` and returns `true`, and `DB::connection('clickhouse')->select('SELECT ? > 1 ?? 10 : 20 AS t', [5])` returns `[['t' => 10]]`, because `??` is a literal `?`. A `?` inside a string literal, a quoted name, a heredoc such as `$$...$$` or a comment is not a placeholder.
- Laravel's query builder failed on several values: `where('flag', false)` sent nothing after the `=`, an insert with `null`, an array or an empty array failed, and `toRawSql()` failed with `Call to a member function quote() on null` for a string and showed `#@1` for a number. These values are now written as literals: `insert(['id' => 10, 'field_two' => false, 'tags' => ['p', 'q'], 'comment' => null])` sends `insert into "my_table" ("comment", "field_two", "id", "tags") values (null, 0, 10, ['p', 'q'])`, and `toRawSql()` gives `select * from "t" where "name" = 'it\'s' and "f" = 0.30000000000000004`. A date, a boolean, an enum, a `Stringable` value and a value object or an expression of the smi2 client are written as literals of their kind, such as `18446744073709551615` for `UInt64::fromString('18446744073709551615')` and `now()` for `new Raw('now()')`. `QueryExecuted::toRawSql()`, which a `DB::listen()` callback can call, gives the SQL with its bindings written in.
- `Connection::escape()` failed with `Call to a member function quote() on null`, because it needs PDO, and so did `toRawSql()`, `dumpRawSql()` and `DB::getRawQueryLog()` for a string value. It now writes ClickHouse literals: `escape("it's")` returns `'it\'s'`, `escape(0.1 + 0.2)` returns `0.30000000000000004`, `escape([1, 'a', null, [2.5, true]])` returns `[1, 'a', null, [2.5, 1]]`, `escape(NAN)` returns `nan`, and `escape("\xff\x00A", true)` returns `x'ff0041'`, a hex string literal that ClickHouse also reads in `VALUES`. 3.0.0 threw a `RuntimeException` for an array and for a binary value. A string with a NUL byte or invalid UTF-8 still throws a `RuntimeException` unless you escape it as binary.
- `unprepared()` and `cursor()` failed with `Call to a member function exec() on null` and `Call to a member function prepare() on null`, and so did the `cursor()` of the query builder and of Eloquent. `unprepared()` now sends the SQL exactly as written and returns `true`.
  - `cursor()` yields the rows of a `SELECT` one by one, as associative arrays, as `select()` returns them, with flat memory. It sends the query with `FORMAT JSONEachRow` on a line of its own, without a trailing `;`, downloads the result into `php://temp`, which keeps up to 2 MB in memory and moves to a temporary file above that, and decodes each row as it yields it: on ClickHouse 24.8, two million rows of an `id` and a string took 2 MB more memory, where `select()` took 193 MB for 200,000 of them. The whole result is downloaded before the first row is yielded, so it must arrive within `timeout_query`. `lazy()`, `lazyById()` and `chunk()` still read page by page.
  - An error that ClickHouse reports throws a `ClickHouseDB\Exception\DatabaseException` with its code and message before any row is yielded, also when the query fails after its first rows (24.8, 26.3 and 26.8 checked), such as `Value passed to 'throwIf' function is non-zero: ... (FUNCTION_THROW_IF_VALUE_IS_NON_ZERO)` followed by the SQL. A timeout or a refused connection throws the smi2 client's `ClickHouseDB\Exception\QueryException`.
  - A query with a `FORMAT` clause, `JSON` included, throws an `Oralunal\LaravelClickHouse\Exceptions\QueryException` before anything is sent: `Cannot read the rows of a query whose FORMAT clause names CSV with cursor(): cursor() asks for the result in JSONEachRow itself and yields its rows one by one. Leave the FORMAT clause out.`
  - A string that is not valid UTF-8, such as a binary MD5 hash, is yielded as `select()` returns it, with U+FFFD in place of the invalid bytes: `SELECT unhex('C328') AS bad` gives `['bad' => "\u{FFFD}("]`. The request asks for this with `output_format_json_validate_utf8=1`, except for a read-only user, the connection's `readonly` option, for whom PHP replaces each invalid byte, so such a string can hold more U+FFFD than `select()` gives.
  - The query is logged once with its bindings. While the connection pretends, it is logged, and nothing is sent or yielded.
- `DB::connection('clickhouse')->select()` let the smi2 client look for a format name anywhere in the SQL, so a query whose string literal, quoted alias or trailing comment named a format returned no rows or failed: `select("SELECT id FROM t WHERE note = 'export as format csv please'")` threw ``QueryException: Can`t find meta``, ``SELECT id AS `format JSON` FROM t`` returned `[]`, and `SELECT id FROM t -- c` put the client's `FORMAT JSON` inside the comment and returned `[]`. These queries, and those of the query builder, now return their rows. A `SELECT` that fails after its first block of rows throws a `DatabaseException` with ClickHouse's error code and name, without the JSON text that ended its message. Raw SQL that ends with a `FORMAT` clause other than `JSON`, `JSONStrings`, `JSONCompact` and `JSONCompactStrings` still cannot be read by `select()`, and now throws before it is sent (see Changed).
- `whereDay()` and `whereMonth()` failed with `TYPE_MISMATCH` (`Cannot convert string '05' to type UInt8`), because Laravel binds a padded text, and `whereTime()` failed with `UNKNOWN_FUNCTION`, because ClickHouse has no `time()`. They now send ClickHouse's functions: `whereDay('created_at', 5)` sends `toDayOfMonth("created_at") = 5`, `whereMonth('created_at', '02')` sends `toMonth("created_at") = 2`, and `whereTime('created_at', '>=', '9:05')` sends `formatDateTime("created_at", '%H:%i:%S') >= '09:05:00'`, which compares the time of day to the second in the column's time zone. `whereDate()` sends `toDate32("created_at")` instead of `date("created_at")`, so it also matches the `Date32` and `DateTime64` values before 1970 and after 2149, where `date()` wraps around, and `whereYear()` sends `toYear()` instead of `year()`, with the same rows. Inside a join closure, Laravel's own `JoinClause` still binds `'05'` for `whereDay()` and `whereMonth()`, which fails as before.
- `inRandomOrder()` sent `RANDOM()`, which failed with `UNKNOWN_FUNCTION`. It now sends `order by rand()`. A seed throws an `InvalidArgumentException`, because `rand()` ignores its argument, and the message shows how to order by `cityHash64(?, id)` instead.
- `union()` sent a bare `union`, which ClickHouse rejects with `EXPECTED_ALL_OR_DISTINCT` unless `union_default_mode` is set, and a union with its own `orderBy()`, `limit()` or `offset()`, as `first()`, `paginate()` and `chunk()` set them, failed with a syntax error. `union()` now sends `union distinct`, which drops duplicate rows as Laravel documents, or a bare `union` when the connection's `settings` set `union_default_mode`; `unionDistinct()` always sends `union distinct`. A union with an order, a limit or an offset is selected from: `select * from ((select "id" from "t" where "id" = 1) union distinct (select "id" from "t" where "id" = 2)) order by "id" desc limit 1`. `delete()` and `update()` still refuse a union.
- `whereNullSafeEquals()` and the `<=>` operator failed, because ClickHouse has `<=>` only in the `ON` of a join, and the bitwise operators failed with `Unrecognized token: '&'`. `whereNullSafeEquals('note', null)` now sends `["note"] = [null]`, which matches the `NULL` rows, and a value other than `null` sends `"note" = 'n2'`, which can use the primary key; `<=>` in `where()` and `having()` works the same way. `where('flag', '&', 1)` sends `bitAnd("flag", 1) != 0`, `|`, `^`, `<<` and `>>` send `bitOr()`, `bitXor()`, `bitShiftLeft()` and `bitShiftRight()` the same way, and `&~` sends `bitAnd("flag", 1) != "flag"`, in `where()` and `having()`.
- `delete($id)`, and `delete()` or `update()` with a column name that names the table, such as Eloquent's qualified key or `updated_at`, failed with `UNKNOWN_IDENTIFIER` (`Missing columns: 'my_table.id'`). `delete()` and `update()` now drop the table's name, with its database, and the table's alias from their column names: `delete(5)` sends `alter table "my_table" delete where "id" = 5`, `where('my_table.id', 5)->update(['my_table.field_one' => 'x'])` sends `alter table "my_table" update "field_one" = 'x' where "id" = 5`, and `table('my_table as t')->where('t.id', 2)->delete()` sends `alter table "my_table" delete where "id" = 2`, where the alias was a syntax error. A sub-query keeps its names, and `whereRaw()` is sent as written.
- `truncate()` kept the alias of the table, so `table('db.examples as e')->truncate()` sent `truncate table "db"."examples" as "e"`, which ClickHouse rejects with a syntax error. It now writes the table without its alias: `truncate table "db"."examples"`. With the `use_on_cluster` option it adds `on cluster '<cluster_name>'` (see Added).
- A `cluster_name` of spaces gave `ON CLUSTER ' '`, which ClickHouse rejects, and a `cluster_name` with spaces around it, as an `.env` value can have, such as `' company_cluster '`, gave `ON CLUSTER ' company_cluster '`, which failed with `CLUSTER_DOESNT_EXIST`. A blank `cluster_name` now counts as none, and the name is trimmed, in the schema builder and the mutations alike, and `Connection::getClusterName()` returns `'company_cluster'`.
- **Data safety:** `Schema::createDatabase()`, `Schema::dropDatabaseIfExists()`, and the `DROP` statements of `Schema::dropAllTables()` and `Schema::dropAllViews()`, which `migrate:fresh` and `db:wipe` run, sent their statements to the nodes without the connection: they were not logged, fired no `QueryExecuted` event and no `beforeExecuting()` callback, and ran while the connection pretended. They now go through `Connection::statementOnEveryNode()`, so they are logged once, fire the event and the callbacks, and send nothing while pretending. They still reach every node; on a connection with a `cluster_name`, as one statement with `ON CLUSTER` (see Changed).
- With the `migrations` table on a ClickHouse connection and the packaged `fix_default_query_builder` on, `migrate:rollback`, with or without `--step`, `--batch` or `--pretend`, `migrate:refresh --step`, and the repository's `getLast()`, `getMigrations()` and `getMigrationsByBatch()` failed with `Call to undefined method ClickHouseDB\Statement::all()`, because Laravel's migration repository read the table with the package's query builder. The package now binds `Oralunal\LaravelClickHouse\ClickhouseMigrationRepository` as `migration.repository`, which reads the table with the query builder, as in `select max("batch") as "aggregate" from "migrations"` and `select * from "migrations" where "batch" = ? order by "migration" desc`, and returns the migrations as objects. Every migration command works, on the default connection and with `--database` (24.8, 26.3 and 26.8 checked) (see Changed).
- **Data safety:** `migrate:refresh`, and any migration command right after a rollback, could read a rolled-back migration as run and skip it, because Laravel's migration repository deleted its row with an `ALTER TABLE ... DELETE`, which ClickHouse runs in the background: on ClickHouse 24.8, `migrate:refresh` ran only the second of two migrations again, and the table of the first stayed dropped. The repository now deletes the row with `mutations_sync = 1`, so the delete returns once the active node has deleted it (see Changed).
- **Data safety:** With asynchronous inserts, the default of ClickHouse 26.3 and 26.8, and `wait_for_async_insert = 0` in the connection's `settings` or the user's profile, an insert returns before its rows are written. So the row that the migration repository logged, and the rows of the `migrations` table that `migrate` loads from a schema dump, could be missing when the next command read the table: a migration ran again, and `migrate` failed to load a dump with `TABLE_ALREADY_EXISTS`. The repository's insert now carries `async_insert = 0` (see Changed), and each `INSERT INTO <table> VALUES` of a dump is sent with `SETTINGS async_insert = 0` before `VALUES`, so that their rows are written when the call returns, whatever the settings say. An `INSERT` of the dump with `SETTINGS`, a `FORMAT` clause or a `SELECT` of its own is sent as it is. The dump file is unchanged, and a dump that 3.0.0 wrote loads the same way.
- **Data safety:** `php artisan clickhouse:install-skills` deleted the files of the directory that a skill directory links to, when the skill directory, such as `.claude/skills/lc-upgrade-3x-to-4x`, was a symbolic link. It now removes the link only, and copies the skill in its place.

### Security

- `min()`, `max()`, `sum()`, `avg()`, `average()` and `aggregate()` quote a string column as a column name, so a column taken from user input, as in `->max($request->metric)`, no longer adds SQL to the query or reads other tables. This is **Breaking** for SQL passed as a string (see Changed).
- The `update()` and the inserts of the package's query builder and models wrote each column name between backticks without escaping it: `update()`, `insert()`, `insertAssoc()`, `insertBulk()`, `create()`, `save()` and `flushBuffer()`. A column name taken from user input, such as a key of `$request->all()`, could therefore end the identifier early and add SQL to the statement, for example to change other columns or every row of the table. The query builder, which every write now goes through, quotes each name as one identifier, between double quotes with its double quotes and backslashes doubled, in `update()`, both insert formats and `insertFiles()`: ``update(['we"ird' => 'x'])`` sends ``alter table "t" update "we""ird" = 'x' ...``. A Nested name such as `n.a` stays one column.
- Laravel's query builder handed its bindings to the smi2 client, which wrote a `Stringable` value without quotes and replaced `:0`, `{0}` and the like anywhere in the SQL, string literals and names included. `where('id', Str::of('0 or 1 = 1'))` sent `"id" = 0 or 1 = 1` and matched every row; it now sends `"id" = '0 or 1 = 1'`. With 41 bindings, as in `whereIn('id', range(100, 140))->orWhereRaw("name = 'a:30'")`, the literal became `'a130'`, and `update(['{0}' => 'ABC'])` sent `update "ABC" = 'ABC'`; both are now sent as written. Raw SQL with named bindings, `:name` or `{name}`, still goes to the smi2 client, but the bindings are made safe first: a `Stringable` value, such as `Str::of("x'y")`, is quoted, where 3.0.0 wrote it without quotes; `false` is `0`, where 3.0.0 wrote nothing; and a backed enum is its quoted value, a pure enum its quoted name, `DB::raw()` its SQL, a `DateTimeInterface` its text and `NAN` `nan`, where 3.0.0 failed or wrote the value without quotes. `null` still leaves the placeholder in place, a collection is still sent as its JSON text, and a float still has 14 significant digits.
- `BaseModel::optimize()` wrote its partition between single quotes without escaping it, so `optimize(true, "a'b")` failed with a syntax error, a backslash was read as an escape, and a value taken from user input could add SQL to the statement. `optimize()` of the query builder and of models writes the partition as `delete()` writes `IN PARTITION`: a string as an escaped string literal, `partition 'a\'b'`, an integer as a number, `partition 202401`, and `DB::raw("ID '202401'")` as the SQL it holds.

## [3.0.0] - 2026-10-08

3.0 renames the package and its namespace. Nothing else changes for your code. The quickest way to upgrade is `/lc-upgrade-2x-to-3x`; see [UPGRADE.md](UPGRADE.md).

### Changed

- **Breaking:** The package is now published as `oralunal/laravel-clickhouse`, and the GitHub repository is `oralunal/laravel-clickhouse`. 2.0.2 is the last release of `oralunal/phpclickhouse-laravel`; that package is abandoned and its existing releases stay installable. `oralunal/laravel-clickhouse` conflicts with it, so Composer never installs both.
- **Breaking:** The namespace moves from `PhpClickHouseLaravel\` to `Oralunal\LaravelClickHouse\`, including the bundled `ClickhouseBuilder`, `ClickhouseSchemaBuilder` and `Enum` and the `raw()`, `tp()` and `array_flatten()` helpers. Class names below the namespace, configuration, the generated SQL and the behavior are unchanged. Values serialized with the 2.x class names, such as cached or queued `RawColumn` objects, cannot be unserialized by 3.0.

### Added

- The `lc-upgrade-2x-to-3x` coding-agent skill, installed by `php artisan clickhouse:install-skills`. Running `/lc-upgrade-2x-to-3x` makes the agent switch the package, rename the namespace across the application, refresh Laravel's caches and verify the result. `/plc-upgrade-1x-to-2x` stays for 1.x applications and now points to it as the next step.

### Fixed

- On a `cluster` connection, `Migration::createMergeTree()` created a table that was not replicated when the callback set the engine by name, for example `->engine(Engine::REPLACING_MERGE_TREE, 'version')`. The table became `ReplacingMergeTree` instead of `ReplicatedReplacingMergeTree`, so its rows were not replicated between the nodes. Setting the engine by name now keeps the replication. An `Engine` instance passed to `engine()` is still used as given. Existing tables are not changed, but wherever the migration runs again (a fresh install, CI, `migrate:fresh`) it now creates the replicated table.

## [2.0.2] - 2026-10-08

### Fixed

- Parallel test runs (`php artisan test --parallel`, `pest --parallel`) no longer let one process drop the ClickHouse tables of another. Since 2.0.1, `migrate:fresh`, and with it `RefreshDatabase` and `LazilyRefreshDatabase`, also empties secondary ClickHouse connections. Every process used the same ClickHouse database, so tests failed at random with `TABLE_ALREADY_EXISTS` or `UNKNOWN_TABLE`. Now each process gets its own database on every secondary ClickHouse connection, named `<database>_test_<token>` like Laravel's per-process database for the default connection.
  - A process creates the database for its first test case that uses a database testing trait, and keeps using it for its other test cases.
  - `--recreate-databases` drops it before the run, `--drop-databases` drops it after the run, and `--without-databases` keeps the configured database.
  - Test runs without `--parallel` are unchanged.
- Parallel test runs with ClickHouse as the default connection failed in every database test with `Database <database>_test_<token> does not exist. (UNKNOWN_DATABASE)`. The ClickHouse schema builder now supports `Schema::createDatabase()` and `Schema::dropDatabaseIfExists()`. It also reports a failed `Schema::hasTable()` as an `Illuminate\Database\QueryException`, so Laravel creates the per-process database as it does for other drivers.

## [2.0.1] - 2026-10-08

2.0.1 completes the 2.0 release. 2.0.0 was tagged from an earlier commit, before the schema builder and the enum base class were bundled, and was only available for a few hours. If you are upgrading from 1.x, go straight to 2.0.1 and follow [UPGRADE.md](UPGRADE.md). Apart from Laravel, the only remaining dependency is `smi2/phpclickhouse`.

### Changed

- **Breaking:** The schema builder used by `Migration::createMergeTree()` now ships inside this package under the `PhpClickHouseLaravel\ClickhouseSchemaBuilder` namespace. It is copied from `glushkovds/php-clickhouse-schema-builder` 1.1.1, which is no longer installed. The DDL it generates is unchanged. Migrations that import `PhpClickHouseSchemaBuilder\Tables\MergeTree` or `PhpClickHouseSchemaBuilder\Expression` must switch to the new namespace.
- **Breaking:** The builder's enums (`Operator`, `Format`, `JoinType`, `JoinStrict`, `OrderDirection`) now extend `PhpClickHouseLaravel\Enum\Enum`, which is copied from `myclabs/php-enum` 1.8.5. They used to extend `MyCLabs\Enum\Enum`, and `myclabs/php-enum` is no longer installed. Their constants and methods are unchanged.
- **Behavior change:** if MySQL or PostgreSQL holds the `migrations` table, `migrate:fresh` now also empties the ClickHouse databases your migrations write to, along with any ClickHouse database that has a dump in `database/schema`. Before, it left them untouched. Migrations written with `CREATE TABLE IF NOT EXISTS` therefore kept their ClickHouse data across `migrate:fresh`; that data is now dropped. The command keeps its production confirmation.

### Added

- `php artisan clickhouse:install-skills` installs the package's coding-agent skills into every agent it finds in the project.
  - It detects agents from their project files (`.claude/`, `.cursor/`, `.github/copilot-instructions.md`, `AGENTS.md`, …).
  - It writes `SKILL.md` to each agent's skills directory.
  - `--agent=` chooses the agents explicitly.
  - The first skill is `plc-upgrade-1x-to-2x`. Running `/plc-upgrade-1x-to-2x` in Claude Code, Cursor, Copilot, Codex and the other agents makes the agent carry out this upgrade and verify it.
- `php artisan migrate:fresh` and `php artisan db:wipe` now work on ClickHouse connections. Previously they failed with `This database driver does not support dropping all tables`. `Schema::dropAllTables()` drops every table, materialized view, view and dictionary on every node, ordering the drops so that ClickHouse accepts them. Views are dropped too, so the dump and the migrations can recreate them. `Schema::dropAllViews()` drops only views and materialized views.
- Secondary ClickHouse connections now follow the connection that holds the `migrations` table. A ClickHouse connection is secondary when a migration in the migrator's paths targets it or when `database/schema` has a dump for it.
  - `schema:dump` also writes `database/schema/<connection>-schema.sql` for each secondary connection.
  - When `migrate` loads the primary dump, each empty secondary connection is loaded from its own dump. If a secondary has no dump, its migrations are marked as pending again and run.
  - `migrate:fresh` empties the secondary connections as well.
  - ClickHouse connections that no migration or dump refers to are never touched.

### Removed

- The `glushkovds/php-clickhouse-schema-builder` and `myclabs/php-enum` dependencies.

### Fixed

- `DB::connection('<name>')->table(...)` on a ClickHouse connection other than `clickhouse` ran its queries against the `clickhouse` connection. Models with a non-default `$connection` logged their queries there as well. Because of this, `migrate --database=<name>` read and wrote the wrong `migrations` table. Query builders are now bound to the connection that created them.

### Upgrade note

- From 1.x: see [UPGRADE.md](UPGRADE.md), or run `php artisan clickhouse:install-skills` and then `/plc-upgrade-1x-to-2x` in your coding agent.
- From 2.0.0: replace `PhpClickHouseSchemaBuilder\` with `PhpClickHouseLaravel\ClickhouseSchemaBuilder\` in your migrations. If your own code uses `myclabs/php-enum`, require it yourself.

## [2.0.0] - 2026-10-08

2.0.0 was tagged before the schema builder and the enum base class were bundled. If you are upgrading from 1.x, go straight to 2.0.1.

### Changed

- **Breaking:** The query builder now ships inside this package under the `PhpClickHouseLaravel\ClickhouseBuilder` namespace. It no longer comes from the `oralunal/clickhouse-builder` dependency, and the `Tinderbox\ClickhouseBuilder` namespace is gone. The SQL it generates is unchanged.
- **Breaking:** The helper functions `raw()`, `tp()` and `array_flatten()` are no longer global. They now live in the `PhpClickHouseLaravel\ClickhouseBuilder` namespace.

### Removed

- **Breaking:** The parts of the old builder that needed the `the-tinderbox/clickhouse-php-client` HTTP client are not included, and that client is no longer installed. This removes `BaseBuilder::addFile()`, `values()`, `getValues()` and `getFiles()`, the `into_memory_table()` and `file_from()` helpers, the client-based `Query\Builder`, and the old builder's Laravel integration. This package's own `Builder` never sent those files to ClickHouse, so these methods could not work here. `whereIn()`, `preWhereIn()`, `whereGlobalIn()` and `havingIn()` used to turn a string that matched a temporary file into a table reference. They now always treat a string as a value. Because no file could be added, that branch never ran.
- The old builder's auto-discovered `ClickhouseServiceProvider` no longer gets installed. It registered a second `clickhouse` database driver with its own `Connection` class. This package's driver only took effect because its provider happened to boot later.

### Fixed

- `Column::subQuery()` and `Column::getSubQuery()` declared the client-based `Query\Builder` as their return type. Building a column sub-query from this package's `Builder` therefore threw a `TypeError`. They now return `BaseBuilder`.

### Upgrade note

- Replace `Tinderbox\ClickhouseBuilder\` with `PhpClickHouseLaravel\ClickhouseBuilder\` in your `use` statements, for example `Query\Expression`, `Query\Enums\Operator` and `Query\TwoElementsLogicExpression`.
- If you called the global `raw()`, import it with `use function PhpClickHouseLaravel\ClickhouseBuilder\raw;`, or use `new RawColumn(...)` or `new Expression(...)` instead.
- If your app requires `oralunal/clickhouse-builder` directly, remove it. The bundled copy replaces it.

## [1.5.0] - 2026-10-08

### Added

- `php artisan schema:dump` now works on ClickHouse connections, including `--prune`, `--path` and `--without-migration-data`. Previously it failed with a `BadMethodCallException` because the connection had no schema state. The dump uses HTTP only, so no `clickhouse-client` binary is needed. It lists tables, dictionaries, views and materialized views in dependency order and appends the rows of the migrations table. References written as `<database>.<table>` lose the database prefix when they point at the connection's own database, so you can load the file into a database with a different name.
- `php artisan migrate` loads `database/schema/<connection>-schema.sql` into a ClickHouse database where no migrations have run yet, then runs only the newer migrations. On a `cluster` connection, the statements go to every node, the same way `Migration::write()` does. `Connection::getSchemaState()` exposes the same loader for apps where ClickHouse is not the default connection.

### Fixed

- `Schema::drop()` and `Schema::dropIfExists()` on a ClickHouse connection used to do nothing, without any error, because the schema grammar could not compile them. They now run `DROP TABLE` and `DROP TABLE IF EXISTS`. A migration whose `down()` relied on these calls now really drops the table.

## [1.4.0] - 2026-08-20

### Fixed

- A published `config/clickhouse.php` is now actually read. The service provider only ever loaded its own bundled copy, so `php artisan vendor:publish --tag=clickhouse-config` followed by editing the file silently did nothing — including the documented way to declare a second ClickHouse connection. Precedence is now `config/database.php` > published `config/clickhouse.php` > packaged defaults.
- `insertBulk()` no longer drops the cast for the first column. `array_search()` returns index `0` for it, which the truthiness check treated as "not found", so a `boolean` cast on the first column was skipped and the raw PHP value reached ClickHouse (typically failing with `Cannot parse string 'false' as UInt8`).
- `flushBuffer()` no longer throws `Fields not match` when rows were buffered one at a time carrying the same keys in different orders. Buffered rows are reordered to the first row's key order at flush time. A row whose key *set* differs is left untouched, so a genuinely mismatched buffer still fails loudly instead of shipping fabricated column values.

### Upgrade note

- If you published `config/clickhouse.php` before this release and edited it, those edits had no effect and may have been worked around elsewhere (for example in `.env` or `config/database.php`). They now take effect, ranking above the packaged defaults and below `config/database.php`. Review the published file before deploying.

### Documentation

- Corrected the derived table name (`MyTable` resolves to `my_tables`, not `my_table`), the events section (only `create()` fires `creating`/`created`; `save()` fires just `saved`), the `InsertArray` example (`insertAssoc()` takes `column => value` rows), and the `$tableSources` comment (`UPDATE` and `TRUNCATE` target it as well).
- Added the missing `PhpClickHouseSchemaBuilder` imports to the Schema Builder migration example, which fataled when copied as written.
- Documented the `cluster_name` connection key, which `Migration::createMergeTree()` reads to emit `ON CLUSTER` and which appeared in no documentation — including the fact that it requires `->ifNotExists()`, since migrations are dispatched to each node in turn and `ON CLUSTER` already creates the table everywhere on the first dispatch.

## [1.3.0] - 2026-08-20

### Changed

- Consolidated duplicated internal scaffolding into shared helpers; public API and generated SQL are unchanged:
  - `Builder`: `delete()`, `update()`, and `insert()` resolve their target table through one protected `getTableForWrites()` helper (previously three copies, one with a divergent string cast).
  - `BaseModel`: `where()` and `whereRaw()` build their entry query through a shared protected static `newSourcedQuery()` helper; `select()` deliberately keeps its previous behavior (no sources table attached).
  - `Migration::createMergeTree()` reads the database name and cluster settings from the resolved `Connection` instead of re-fetching them from the global `config()` repository.
  - `WithClient::getThisClient()` now routes through `resolveConnection()`, and the deprecated static `getClient()` delegates to `getThisClient()`. For subclasses that override `resolveConnection()` or `getThisClient()`, the override now consistently applies to every client acquisition; previously some internal paths bypassed it.

## [1.2.0] - 2026-05-07

### Added

- In-memory buffered inserts on `BaseModel`: `buffer()` accumulates rows per-model and `flushBuffer()` sends them to ClickHouse as a single `insertAssocBulk` HTTP request. The `$casts` pipeline used by `insertAssoc()` is reused, so cast behavior is identical. On flush failure the buffer is preserved so the caller can retry.
- Helper methods alongside the buffer API: `bufferCount()`, `getBufferedRows()`, `clearBuffer()`, and `BaseModel::flushAllBuffers()`.
- Auto-flush on script shutdown: the service provider registers a Laravel `terminating` callback plus a `register_shutdown_function` fallback for non-HTTP scripts. Errors during auto-flush are reported via `report()` rather than thrown.

### Changed

- Extracted the row-normalization + cast loop from `insertAssoc()` into a shared `prepareAssocRowsForInsert()` helper so manual and buffered inserts go through the same path. Public behavior of `insertAssoc()` is unchanged.

## [1.1.0] - 2026-04-17

### Added

- Package auto-discovery — the service provider registers itself via `extra.laravel.providers`, so no manual entry in `config/app.php` / `bootstrap/providers.php` is needed.
- Multi-connection support in the publishable `config/clickhouse.php`. Each entry is merged into `config('database.connections.<name>')`; user-supplied values always win.
- Unit-level test coverage for `QueryGrammar`, `SchemaGrammar`, and `Builder` SQL generation — these run without Docker / ClickHouse.
- GitHub Actions CI workflow against real ClickHouse service containers, with cluster tests gated off in CI.

- Replaced the `tests.bootstrap.sh` + `bitnami/laravel` container flow with a slimmed-down `docker-compose.test.yaml` that only runs ClickHouse + Zookeeper.

### Removed

- Legacy `.travis.yml` and `.github/workflows/test.yml`.
